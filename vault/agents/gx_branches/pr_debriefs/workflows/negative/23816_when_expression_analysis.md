# #23816 Match workflow `when` inputs by path instead of substring

https://github.com/galaxyproject/galaxy/pull/23816. Branch `when_expression_analysis`. Opened
2026-09-30 and now a draft. +692/-19 across 8 files. The branch's commits date from 2026-08-21
and 2026-09-04, so it waited about four weeks before opening. #23817 (server-side import
validation) was stacked on it, and John closed #23817 once this PR stalled. `optional_input_gating`
is also stacked on it.

## What happened

- The editor's `step.when?.includes(inputName)` substring check was replaced with a hand-written
  tokenizer (`whenExpression.ts`), path mapping (`workflowInputPath.ts`) and a shared
  `when_expression_spec.yml`.
- mvdbeek's single inline thread, on `whenExpression.ts:4`, asked three things:
  1. "these aren't expression written by hand, right? … they're AI? Can we simply fail these and
     reduce the complexity?"
  2. "I had also hoped we'd compile when expressions against the tool input schema like we do in
     the custom tool editor, did you explore this option?"
  3. A link to #23428: "we're calling something a bug that we never explicitly supported? The
     stance was we'll start with simple boolean input and build out a UI and validation around
     it."
- The thread then went off course:
  - John: "totally unrelated to #23428." mvdbeek: "isn't this all about hand-written
    pipe-delimited identifiers?"
  - John: "The PR description didn't mention this once… Pipes didn't drive any of this
    development". He then conceded that the comment at that line "does give me the ick".
- John posted a long agent-written, agent-fact-checked analysis of compiling vs tokenizing, inside
  `<details>`. It concludes that static analysis is still needed for missing tools, and offers
  options A–E, including mvdbeek's scope cut (E).
- No reply since. A human-voiced response is drafted in `gx_branches/23816_response.md`.

## Why it stalled

1. **The PR solved a problem the reviewer doesn't believe exists.** The project's stated stance
   is that `when` is a simple boolean, generated by the UI. The PR treats free-form expressions as
   a supported input and calls their mis-handling a bug. It never says who writes these
   expressions: imports, the API, gxformat2 authors, agents. The same question had already been
   asked on #23428 ("have you run into a case like this in the wild?") and never answered. This
   PR inherited the doubt.
2. **The size didn't match the claimed scope.** It added 692 lines, including a JS tokenizer, to
   fix a substring check. A reviewer who sees "parser" assumes the project is now committed to
   parsing arbitrary JS. A smaller alternative exists in John's own branches
   (`when_input_exact_match`) but wasn't offered.
3. **One agent-written code comment pulled in an unrelated controversy.** The comment at line 4
   mentions pipe or legacy spellings. That tied the PR to the #23428 debate the author never
   intended to touch. The reviewer anchors on what the code says, not on what the description
   leaves out.
4. **The obvious alternative wasn't pre-empted.** mvdbeek had "hoped" for schema compilation,
   following the custom tool editor. The PR didn't say whether that had been considered. The
   answer came afterwards, as a huge agent document, which reads as heavier than the question.
5. **What the reviewer had asked for was stacked behind what he hadn't.** On #23409, mvdbeek asked
   specifically for readable errors when agents upload invented expressions. That is #23817, and
   it was built on top of #23816. So the requested fix waited on the debated one, and the next
   step was to close #23817.
6. **The thread turned adversarial.** "The PR description didn't mention this once" reads as a
   rebuttal. Replies in the reviewer's own frame ("you're right that the UI never authors these,
   and here's why we still have to handle them") de-escalate.
7. **The branch was stale when it opened.** The ~4-week delay meant the reviewer's model had moved
   (the #23428 "never supported" stance arrived 2026-09-11) by the time the PR appeared.

## What could have prevented it

- **Open the server-side validation PR (#23817) first, standalone**, as the direct answer to his
  #23409 question. It needs only the generated forms plus a simple reference check. Ship the thing
  the reviewer asked for first.
- **Establish that the problem exists before the fix.** Find real workflows (IWC, usegalaxy.*
  published workflows, gxformat2 test data) with free-form `when` expressions, and cite them. If
  there are none, adopt the scope cut and say so.
- **Offer the small fix first, and the large one as optional.** `when_input_exact_match` for the
  generated forms, with expressions it can't parse treated as dynamic (keep the terminal). Make
  the tokenizer a follow-up that has to earn its place.
- **Add a "Why not X?" section** covering the known reviewer preferences, here the custom tool
  editor's schema compilation. Two sentences up front beats a 3,000-word reply.
- **Audit agent-written comments for scope creep before opening.** Any comment that mentions a
  contested topic (pipes, legacy syntax) will be read as intent.
- **Reply in human voice and short.** Link the agent analysis rather than inlining it. Lead with
  agreement on the reviewer's premise before the disagreement. `23816_response.md` already moves
  this way.
- **Rebase and re-check context before opening an aged branch.** Re-read the reviewer's latest
  comments on related threads (#23428, #23409) and adjust the framing.

## Signal

The reviewer's objection was about **scope and support policy**, not code quality, and the
response defended the implementation. When the objection is "should we support this at all",
answer with evidence of need and a smaller option, not a better argument for the large one.
