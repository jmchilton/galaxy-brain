# Triage a Foundry issue

Label rules live in Foundry, not here: [`content/meta/issue-labels.md`](https://github.com/galaxyproject/foundry/blob/main/content/meta/issue-labels.md). Read it first from current main (`git -C ~/projects/repositories/foundry fetch -q origin && git -C ~/projects/repositories/foundry show origin/main:content/meta/issue-labels.md`); the local clone's checkout may be on another branch.

1. Read the issue and its comments (`gh issue view N -R galaxyproject/foundry --json title,body,comments,labels`; `--comments` can print nothing). Check for open PRs or branches that address it (`gh pr list -R galaxyproject/foundry --search N --state all`).
2. Check its claims against code where cheap: read `origin/main`, not the checkout. Don't implement.
3. Choose the labels the doc requires: one `roadmap/*`, one `priority/*`, and either one `work/*` or the blockers. A blocked issue gets no `work/*` label.
   - Parent: for `roadmap/substep`, pick one from `gh issue list -R galaxyproject/foundry --label roadmap/main --state open`. If none fits, propose `roadmap/off` and name the closest candidate; don't force a parent.
   - Upstream bugs: before proposing `upstream/*`, check whether the fix already exists on the upstream's release branches and published packages (PyPI/npm), not just dev/master. Released → propose closing with upgrade guidance instead.
   - We maintain Planemo, gxformat2 and gxwf (galaxy-tool-util-ts). A bug there is work we can do: prefer `work/ready-implement` with the fix aimed at that repo; add `upstream/*` only while waiting on a merge or release.
   - Bugs in repos we don't maintain with no matching `upstream/*` label (e.g. tool wrappers): `roadmap/off` + `work/human`, and say where it should be filed.
4. Derive the vault status per the "Label mapping" in [CLAUDE.md](CLAUDE.md); proposed labels count only once applied. Open questions for John go in the note; they don't change the status.
5. Create the directory and `vault/repositories/foundry/issues/<status>/<number>/index.md`: title, issue link, proposed labels and parent with a reason each, status, findings (what was verified, what wasn't), next. See `issues/*/678/` for shape. Stage the labels and parent not yet on GitHub in `issue_tags.md` beside it ([FILE_DOCS.md](../../repositories/foundry/issues/FILE_DOCS.md)).
6. Upstream issues: draft one issue per upstream problem the issue waits on that has no upstream issue or PR yet. The result is a reviewed description that waits for John's decision. It builds on [`GENERIC_ISSUE_DESCRIPTIONS.md`](../_shared/GENERIC_ISSUE_DESCRIPTIONS.md). Never post the issue without an explicit ask.
   - Write it to `RECORD/upstream_<project>_<shortname>.md`, where RECORD is the record directory and `<project>` the upstream repository's short name (`galaxy`, `planemo`, `tools-iuc`), following `GENERIC_ISSUE_DESCRIPTIONS.md` and that repository's own issue guidelines. If a duplicate is found or it seems like a non-issue, write no proposal; make the case for rejecting it in `index.md` instead.
   - Give a fresh subagent each proposed description and its source material. Ask it to check the description for correctness and clarity against the code and the cited issues and PRs, and to revise it. If anything is egregious, such as a claim that isn't reproduced, a wrong premise, or a duplicate issue, the subagent pushes back instead of polishing the text. Do one review round only. Report anything left over in `index.md` instead of looping.
   - List the proposals in `index.md`'s next steps.
7. Move the issue's line in [MY_ISSUES.md](../../repositories/foundry/issues/MY_ISSUES.md) to the matching section. In batch runs with subagents, the coordinator does this, not the subagents.
8. Don't apply labels or the parent link on GitHub. John applies them with the 🔖 Apply staged labels launcher, or gives his OK.
