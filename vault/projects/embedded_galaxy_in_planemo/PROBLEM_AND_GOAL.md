# Embedded Galaxy Engine for Planemo (`--engine embedded_galaxy`)

## Scope and Assumptions

- **This document assumes [planemo#1678](https://github.com/galaxyproject/planemo/pull/1678) ("Use Gravity multiprocessing for modern Galaxy") is merged**, and is written against that baseline. That work gives the existing `galaxy` engine a real process-lifecycle story - Gravity's `multiprocessing` process manager for Galaxy 25.0.1+, foreground `run.sh` in its own process group behind a `daemon_monitor`, `terminate_process_group` escalation, detach-on-success - and it establishes conventions this engine should follow rather than re-invent. It also introduces the assumption that a Galaxy version can be read off a checkout, which this engine has to break.
- **This is the first engine where Galaxy shares Planemo's Python environment.** Every existing engine keeps them apart - a Galaxy-owned virtualenv, a container, or someone else's server - which is why Planemo's own library versions have never had to agree with the Galaxy under test, and why the `--galaxy_branch` matrix can exercise 23.1 through dev regardless of what Planemo itself resolves. Embedding removes that separation, so packaging questions that were previously nobody's problem become design constraints; they are worked through in `HANDLING_PACKAGE_VERSIONS.md`.
- **The `galaxy` metapackage is the dependency, and its lock is deliberate.** Its published wheel declares all 337 requirements with `==` - 24 `galaxy-*` siblings plus 313 third-party packages drawn from `lib/galaxy/dependencies/pinned-requirements.txt` - which makes it a known-good deployment artifact rather than a composable library, and that is the point. It also makes sibling skew impossible by construction, which is precisely what the individual package wheels cannot offer, since they declare their siblings with no version constraint at all (`packages/app/pyproject.toml:18-30`). Measured cost of depending on it: Planemo's resolution grows from 97 to 350 distributions and moves 34 transitive dependencies backward, with zero conflicts - and every one of those is drift since Galaxy's last release (`certifi 2026.7.22→2026.4.22`, `cwltool 20260720→20260413`, `numpy 2.5.2→2.4.5`), not incompatibility. Running Planemo against the dependency set Galaxy actually tested is a feature of this engine, not a tax on it.
- **Making `embedded_galaxy` the default engine is explicitly out of scope here.** That is the long-term destination, but this document stops at an opt-in engine that reaches functional parity for tool and workflow execution; promoting it - and the compatibility, packaging and messaging work that implies - is a separate decision made once parity is demonstrated.

## Problem

Every Planemo operation that needs a real Galaxy - `planemo test`, `planemo run`, `planemo serve`, `planemo shed_test` - currently pays for an entire out-of-process Galaxy deployment. The default `galaxy` engine downloads or clones a Galaxy source tree into the Planemo workspace, builds a Python virtualenv inside it, writes a config directory, and then shells out to `run.sh`, which starts gunicorn and Celery under Gravity and is polled over HTTP until it answers. That machinery makes the first run of a one-line tool test take many minutes, couples tool development to git, network, virtualenv and client-build state that has nothing to do with the tool being tested, reduces Galaxy's own diagnostics to a tail of a log file that Planemo has to shovel back to the user, and turns most startup failures into an opaque non-zero exit code. It also leaves Planemo with no handle on the Galaxy it just started beyond an API key and a URL, so anything Planemo wants to know about the app - loaded tools, config resolution, why a tool failed to parse - has to be reverse-engineered through the API or the log. Meanwhile Galaxy itself is now published to PyPI as a set of installable distributions, and Galaxy's own test suite has for years started a full application in-process, served by uvicorn on a background thread, in seconds.

## Approach

Add a new peer engine, `--engine embedded_galaxy`, that builds a Galaxy application object inside the Planemo process from the configuration Planemo already generates and serves it with uvicorn on a background thread, so `config.galaxy_url` still points at a genuine local HTTP endpoint and every downstream layer of Planemo - bioblend, the staging interface, the tool test interactor, invocation polling and output collection - keeps working untouched. Galaxy arrives as the locked `galaxy` metapackage behind an optional install extra rather than as a cloned repository, which removes the clone, the virtualenv, `run.sh`, Gravity and the external Celery worker from the critical path entirely while giving Planemo the exact dependency set Galaxy released against. The implementation is a new `EmbeddedGalaxyConfig` satisfying the existing `GalaxyConfig` abstraction alongside `LocalGalaxyConfig`, `DockerGalaxyConfig` and the external variant, sharing - not copying - the config-generation code that `local_galaxy_config` already contains, and adding only what embedding genuinely requires: in-process startup and deterministic shutdown, log capture through Python's logging system instead of a file, and a Celery worker running on a thread inside Planemo in place of one Gravity supervises. The result is the fastest and most debuggable way to run a tool or workflow locally, with a direct application handle available in-process for richer diagnostics later.

## Requirements

1. Register `embedded_galaxy` as a first-class engine: recognized by `build_engine` and `is_galaxy_engine` in `planemo/engine/factory.py`, and offered by the `--engine` choice list in `planemo/options.py` so `run`, `test` and `serve` all accept it.
2. Implement `EmbeddedGalaxyConfig` against the existing `GalaxyConfig` interface - `galaxy_url`, `gi`/`user_gi`, API keys, `install_workflows`, `kill`, `cleanup`, `log_contents` - so that `planemo.galaxy.activity.execute`, the tool-test interactor and the invocation polling code run against it with no changes.
3. Share configuration generation rather than duplicating it. `write_galaxy_config` already separates cleanly into the Galaxy properties every engine needs and the `gravity:` block only a subprocess engine needs, and that split - together with the `tool_conf`, job-config, shed-config and dependency-resolver construction in `local_galaxy_config` - should become a helper both configs consume so the two cannot drift.
4. Import Galaxy lazily behind an optional extra so that CLI startup never imports `galaxy.app` and a missing extra produces an actionable install message rather than a traceback. The extra is a single dependency on the `galaxy` metapackage constrained to one release series (`galaxy>=26.1,<26.2` at time of writing); because that metapackage pins its own siblings exactly, Planemo needs no further pinning of its own and cannot end up with a mixed-series Galaxy.
5. Keep Planemo's own `galaxy-tool-util` upper bound permissive enough to cover the Galaxy series the extra targets, and bump the two together in one commit. This is load-bearing rather than tidy: the metapackage pins `galaxy-tool-util` exactly, so once Galaxy 26.2 ships, `galaxy` 26.2.x will require `galaxy-tool-util==26.2.0` while Planemo's base `<26.2` excludes it - an unsatisfiable resolution, not a downgrade - and an extra can only add requirements, never relax a bound declared in the base requirements.
6. Determine the target Galaxy version without a checkout. Post-#1678 `get_galaxy_version(galaxy_root)` execs `lib/galaxy/version.py` off disk and sits on the config-construction path via `gravity_supports_multiprocessing`, so it needs a seam; the answer for an installed Galaxy is simply `from galaxy.version import VERSION_MAJOR`, which `galaxy-util` ships and Planemo already depends on. That reports `galaxy-util`'s version rather than the application's, which is exact so long as the metapackage supplies the family - one more reason the extra depends on it rather than assembling the distributions itself.
7. Own the application lifecycle explicitly, with a small Planemo-side launcher rather than Galaxy's test-only driver - whose module-level `galaxy_directory()` assumes a source checkout - so production code does not import `galaxy_test.driver`: allocate a free port, start the app and its uvicorn thread, wait for a health check with a bounded timeout, and on teardown shut down the server, join the thread, call the app's shutdown hook and dispose of database connections so Planemo exits without hung threads. Where Galaxy would need a supported embedding entry point to make this clean, record it as an upstream follow-up.
8. Route all Galaxy output through a single captured log stream: attach a handler so in-process logging is what `log_contents` returns, honour `--verbose` by streaming it, and return `{}` from `service_log_contents` - the same shape #1678 established for multiprocessing, where co-located services share the foreground process's output instead of writing separate files.
9. Run Galaxy's asynchronous task machinery rather than opting out of it. This engine does not get to skip Celery: the tool-test interactor forces the asynchronous submission path for every tool whose tests carry the `test_case_json` value-state representation - which is every YAML tool - by overriding `use_legacy_api` outright (`interactor.py:799-800`), and that path posts to `/api/jobs`, which calls `queue_jobs.delay(...)` with no synchronous branch beside it (`services/jobs.py:298`). With nothing consuming the queue the `ToolRequest` never leaves `NEW`, so turning Celery off does not degrade newer tool tests, it hangs them - against an interactor timeout of a day. The engine therefore sets `enable_celery_tasks: true`, runs a worker on a thread inside the Planemo process consuming both `galaxy.internal` and `galaxy.external` (Galaxy's default `task_routes` send `galaxy.fetch_data` and `galaxy.set_job_metadata` to the latter), configures a broker and a result backend explicitly rather than inheriting a deployment's, and tears all of it down - including the forkserver process pool a booting worker creates - as part of engine shutdown. `BACKGROUND_WORK.md` works through the options and their costs.
10. Run without Gravity and without gx-it-proxy: no process manager supervising a worker or a beat scheduler, and interactive tools configured off rather than leaving Planemo's default enablement pointing at a proxy that will never be started. Nothing schedules Galaxy's periodic tasks, which is harmless over the lifetime of a Planemo run and is worth stating so nobody rediscovers it as a bug.
11. Support the options that still make sense for an embedded server - `--extra_tools`, Tool Shed installs, `--profile` and Postgres databases, Conda/container dependency resolution - and fail fast with a clear explanation for the ones that cannot apply.
12. Make `planemo serve --engine embedded_galaxy` a usable interactive server - foreground, prints its URL, and shuts down cleanly on Ctrl-C - so the engine is a development tool and not only a test harness. Backgrounding stays the `galaxy` engine's job, where #1678 now handles it properly.
13. Cover the engine in Planemo's own test suite with at least a tool test and a workflow test executed through it, skipped cleanly when the extra is not installed, and wire a CI job that installs the extra and runs them.
14. Document the engine where the other engines are documented - the engine list in `docs/_running_intro.rst` and the per-engine section in `docs/test_format.rst` - including an honest statement of when to prefer it over `galaxy`, `docker_galaxy` or `external_galaxy`.

## Acceptance Criteria

1. On a machine with no Galaxy checkout and no Planemo-managed virtualenv, `planemo test --engine embedded_galaxy <tool.xml>` passes and leaves no cloned or downloaded Galaxy source tree in the Planemo workspace. The same holds for `planemo test --engine embedded_galaxy <workflow.ga>` where the workflow's tools are installed from the Tool Shed.
2. A YAML tool passes under the engine. Its tests submit through `/api/jobs` and are polled through `/api/tool_requests/{id}/state`, so this is the criterion that demonstrates the asynchronous task path works end to end rather than only that uploads do - and it is the one that fails as a hang, not an error, if the worker is misconfigured.
3. `planemo run --engine embedded_galaxy` produces downloaded outputs equivalent to the `galaxy` engine's for the same artifact and job, and the structured test results - ids, statuses, job data - are indistinguishable in shape, so existing report generation, `--test_output_json`, and `--failed` re-runs work unchanged.
4. Time from command invocation to a responsive Galaxy drops from minutes to seconds on a warm pip cache, measured against post-#1678 master for both cold and warm runs and recorded in the pull request.
5. A deliberately failing tool test surfaces Galaxy's own error output in Planemo's output without requiring the user to hunt through a log file, and a tool that fails to load reports why.
6. Runs terminate cleanly: the correct exit code is returned, no orphaned threads or processes survive the command - the Celery worker thread and the forkserver process pool it creates on boot included - and the temporary config directory is removed unless `--no_cleanup` was requested.
7. `planemo serve --engine embedded_galaxy` brings up a browsable Galaxy at the printed URL, serves the tools under test, and exits on Ctrl-C; combining it with `--daemon` exits non-zero with a message directing the user to `--engine galaxy`.
8. `pip install planemo[embedded_galaxy]` is the documented and tested way to enable the engine; without it, `--engine embedded_galaxy` exits non-zero quoting exactly that command, and `planemo --help` startup time and import graph are unchanged from today.
9. Installing the extra resolves cleanly against Planemo's base requirements, verified in CI by a resolution-only job that needs no Galaxy run - and that job fails loudly on the release where Planemo's `galaxy-tool-util` bound stops covering the Galaxy series the extra targets, which is the one way this dependency can break outright rather than merely shift versions.
10. `--galaxy_root` combined with `--engine embedded_galaxy` is rejected with a message directing the user to `--engine galaxy`; embedding a source checkout is not supported by this engine.
11. Several artifacts tested in a single Planemo invocation run in sequence against the embedded app without state leakage between them, producing the same results as running them one at a time.
12. The existing engines are untouched behaviourally: the full existing test suite passes, and no change is required to `LocalManagedGalaxyEngine`, `DockerizedManagedGalaxyEngine` or `ExternalGalaxyEngine` semantics.
13. The diff shows the shared configuration helper actually shared - no second copy of the Galaxy properties dictionary or of the tool/job/shed config writing logic - and CI runs a tool test and a workflow test under the new engine on every pull request with the documentation building alongside.

## Open Questions

- How does this relate to `uvx_galaxy` ([#1555](https://github.com/galaxyproject/planemo/pull/1555))? Both drop the clone and the virtualenv; that engine keeps Galaxy in a subprocess via `uvx`, this one puts it in-process. Do both ship, does one subsume the other, or do they become one engine with a flag - and either way, #1678 supersedes #1555's `io.py` and engine-`finally` changes and offers `start_daemon`/`detach_daemon` in place of its `nohup … & echo $!` handling. Both engines consume the same locked metapackage, so the packaging story is shared rather than divergent; the one wrinkle specific to `uvx_galaxy` is that it layers `--with-requirements <frozen conditional deps>` on top of a 337-entry `==` lock, which resolves only while the freeze is generated from exactly the release being installed.
- Is exposing the in-process `app` object to Planemo code needed? Let's try to reach parity before adding deep integration specialization for this engine.
