# WF_OPTIONAL_INPUTS_PLAN — implementation debrief

This document records the completed Galaxy-side implementation of [[WF_OPTIONAL_INPUTS_PLAN]]. The
plan itself was not edited; this debrief captures what landed, how it was verified, where the
implementation differs from the plan, and what remains open.

## Outcome at a glance

The branch implements optional-input presence gating across workflow execution fixtures, editor
connection validation, the step form, linting, synthesized gate-port typing, the drop interaction,
Selenium coverage, and developer documentation. The final tip is `bb5c0dbcde`.

The main remaining risks are narrower than the delivered feature:

- synthesized gate ports can retain stale source-derived types after the source step changes;
- the drop dialog and its undo grouping lack direct automated coverage; and
- the branch depends on #23333 (`optional_inputs`) landing first.

For future work in the same editor paths, start with **Reuse map**. For the implementation history,
read **Commit log**. For scope changes and known baseline failures, read **Deviations from the plan**
and **Pre-existing state worth knowing**. The actionable follow-up list is under **What still needs
doing**.

### Verification ladder for adjacent changes

Use the narrowest layer that proves each claim, then add the next layer only for behavior that crosses
it:

1. **Analyzer tests:** truth-table rows plus tokenizer/parser hazards; include cases that must remain
   indeterminate, not just true/false classifications.
2. **Terminal tests:** assert both terminal return values and the
   `connectionStore.invalidConnections` side effect. Pair every accepted case with controls for a
   different input, an inverse gate, and a connection that is invalid for another reason.
3. **Store/component tests:** pin reserved-port typing, generated-expression round trips, custom-gate
   confirmation, and mode availability. Prove new component tests are non-vacuous against the old
   implementation when practical.
4. **Framework workflow tests:** exercise absence/presence, nested access spelling, ungated failure,
   and twin exclusivity. For an expected failure, retain output assertions that prevent a swallowed
   lookup error from passing vacuously.
5. **End-to-end tests:** reserve these for visible marking, authoring controls, save/download, and
   multi-step topology. Do not use an E2E assertion as independent proof of dynamic port
   recomputation until stale gate ports are fixed.

When the broad suite is already red, capture an untouched baseline and compare exact additional
failures rather than weakening the acceptance gate. Preserve the real command's exit status: write
long output to a file instead of piping through `tail`. For E2E work, verify installed client
versions and use a scratch database rather than migrating a worktree's existing development data.

### Phase 1c — the drop shortcut

`a5778713e0` **Offer to gate the step when an optional output is dropped on a required input**

`canAcceptWithPresenceGate` on `BaseInputTerminal` answers a question that `attachable` cannot: would
adding a presence gate resolve this refusal, or is the connection invalid for another reason? It
temporarily enables presence-gated acceptance, re-runs `canAccept`, and clears the private flag in a
`finally`. A collection dropped on a data input, or a value dropped on an already-filled input,
therefore remains refused. Five tests cover the predicate, including one that verifies the terminal
is left ungated afterward.

`NodeInput.vue`'s `onDrop` offers the remedy through `useConfirmDialog`, and accepting makes the
connection and writes the expression inside one `undoRedoStore` action — undo must not leave a gate
reading an input that is no longer connected.

The drop interaction itself has no automated test. `NodeInput.vue` has no Vitest coverage today, and
`workflow_editor_connect` — the selenium drag helper — does not work under the Playwright backend.
The terminal predicate underneath it is covered; the dialog and the undo grouping are not.

### Post-implementation corrections found by re-reading

`5ea76d52f7` **Do not decide a gate that reads a property of the input in question**

The evaluator had bound any access prefixed by the target path to `null`. For example,
`$(inputs.reference.format != "bwa_mem2_index")` — a shape already used by
`directory_index.gxwf.yml` — became `null != "bwa_mem2_index"`. That evaluates to true, so the
analyzer incorrectly concluded that the step runs while the dataset is absent and refused the
connection.

The correction binds only a direct access to the input itself to `null`. Reading a property through
an absent input throws rather than resolving either way, so the analyzer now treats that case as
indeterminate and permits it. Reference detection still uses prefix matching; only null evaluation
changed.

`c8ceaed41f` **Keep the conventional `when` port a required boolean**

Phase 2 infers an extra gate port's `input_type`, `type`, and `optional` from its source. Applying
that rule to the conventional `when` port would remove a real validation check: a text parameter
connected to `when` would turn the destination into a text port, and the editor would no longer
report the mismatch.

The correction keeps `when` a required boolean because it has a fixed meaning. Other extra
connections still inherit their source shape, which is the behavior Phase 2 was intended to add. A
new store test supplies a text source and verifies that the synthesized `when` port remains a
required boolean.

The `when` correction came from code review rather than a failing test: a nearby Selenium assertion
made the consequence of unrestricted source inference visible. The store test added with the fix
confirms the exemption directly. The later E2E run confirms that the user-visible mismatch check
works in the ordinary flow, but cannot distinguish the fixed implementation from unrestricted
source inference because downstream synthesized ports can go stale.

## Deviations from the plan

- **Fixture names omit the `a_` prefix.** The plan says rename `exp_*` to
  `optional_input_gating_*`, which
  read literally gives `optional_input_gating_a_toplevel`. The `a` was design-A shorthand and means
  nothing upstream, so the fixtures are `optional_input_gating_{toplevel,nested_dot,nested_bracket,
  nogate,twin_probe}`.
- **`isPathPrefix` matches in one direction only,** exactly as the plan specifies: the target must be
  a prefix of the referenced access, so `$(inputs.cond.input1 ...)` answers for both `cond` and
  `cond|input1`. The reverse — `$(inputs.cond ...)` answering for target `cond|input1` — is not
  matched. Adding it would be compatible with every row of the plan's truth table and would be more
  consistent with the stated permissiveness principle, but nobody writes a presence gate against a
  conditional's container, so it is left out rather than guessed at.
- **The 1a "verify first" gate was discharged in vitest, not in a browser.** See the commit log
  above. The code path was confirmed live, which is what the plan asked for; what was not confirmed
  is what the marking *looks like* to a user.
- **Three `when` test fixtures were rewritten, and this is the one change worth a second look.**
  `workflowStepStore.test.ts` and `layout.test.ts` spelled their gates `${check_value}`, `${flag1}`,
  `${flag2}` — bare names with no `inputs` reference. Those only ever worked because the matcher
  asked whether the expression *string contained* the connection name. Under path analysis they
  reference nothing, so no gate port is synthesized, and `layout.test.ts` broke: two of its four
  tests failed with "skipping edge with non-existent port(s)". The fixtures are now
  `$(inputs.check_value)` and so on. This is a test-data edit made to keep tests passing, so state
  the reason plainly: a bare name is not a Galaxy `when` expression — the server evaluates the body
  with `inputs` in scope, and a bare identifier is a ReferenceError. No workflow that runs can be
  spelled that way. The alternative — treating "expression mentions no inputs at all" as
  unresolvable and therefore matching everything — would keep the fixtures working but would
  synthesize gate ports for every stray connection on a step gated by `$(true)`.

## Review round

Three reviewers, one per stage of the branch. Their findings and the follow-up fixes exposed a
dozen-plus correctness and coverage defects; three were the dangerous kind — a confident wrong
answer rather than a refusal. Every claim was reproduced before being acted on.

### Analyzer soundness — `f0967c9afa` / `b984fda7a2`

Six analyzer defects were fixed:

- loose equality fell back to strict equality, allowing
  `$(1 == '1' && inputs.x === null)` to be classified as false-when-null even though the step runs
  without the input;
- `&&` and `||` returned booleans instead of JavaScript's operand values, inverting
  `$((inputs.a || inputs.a) !== null)`;
- deeply nested input threw `RangeError` from `attachable` into the render path because only
  `ParseFailure` was caught;
- optional chaining truncated the access path and then treated the truncation as resolved;
- regex bodies were scanned as code, inventing input references and false dangling-gate warnings;
  and
- a trailing semicolon or comment prevented the `$(...)` wrapper from being recognized.

### Repeat-path gate generation — `637ade9021` / `4ecba705c3`

Generated gates were wrong for inputs inside repeats, and an existing test had pinned the wrong
behavior. Galaxy addresses cat1's repeat data parameter as `queries_0|input2`, but splitting that
name on `|` generated `$(inputs.queries_0.input2 !== null)`. Tool state stores `queries` as an array,
so `inputs.queries_0` is undefined and `undefined !== null` evaluates to true. The result was a gate
that always ran without raising an error, while both editor validation and dangling-gate linting
appeared satisfied. The generator now walks tool state and declines to generate expressions for
names it cannot reach.

### Preserving custom gates — `667ef664c7` / `8850e90026`

Two paths could still overwrite a hand-written gate. The confirmation was inside only the clear
path, so both `custom → boolean` and `custom → presence` replaced the expression without a dialog.
The drop handler could likewise replace an existing gate. Both paths now preserve the confirmation
contract. The same fix routes the gate path through `connect`, retaining the map-over setup that a
direct `makeConnection` call skipped.

### Twin fixture validity — `506d53a234`

The twin dispatch fixture could not detect that both twins had run. `first_non_null` chooses
`input_0`, the when-present output, so the first case returned PROVIDED even after deleting the
inverse gate. Replacing it with `the_only_non_null` makes the merge fail unless exactly one twin
produces a value; deleting the gate then fails with `expression_evaluation_failed` as expected.

The same commit removes two unasserted and incorrect claims from the nogate documentation: there is
no `validation_failed` tool-request state, and the parameter error continues beyond the point the
old prose described.

### Twin connection acceptance — `6961d99fd7`

The twin form's tool-parameter connection was still marked invalid. In
`optional_input_gating_twin_probe`, the gate names `probe`, while the dataset arrives on `input1`;
both are fed by the same optional output. The original rule considered only whether the gate named
the destination input, so it refused `input1`.

The corrected rule operates on the shared source output: accept when the step's gate
presence-guards another input fed by the same output being attached. It applies equally to a drag
and an existing connection because both reach `attachable` with the same output terminal. Negative
tests cover an inverse gate on the shared source and a gate on an input fed by a different source.

This extends Phase 1a beyond its literal wording, which mentions a gate referencing *this* input.
The extension is justified by the plan's own supported twin shape; otherwise a fixture delivered by
the branch would remain visibly broken in the editor.

### Missing-tool lint — `6e5c70cd94`

Dangling-gate lint no longer reports every reference on a step whose tool failed to load. With no
inputs and no usable state, the missing tool is the actionable error.

### Documentation and E2E closure — `bba157ed92` / `bb5c0dbcde`

The documentation now explains which gates the editor declines to generate and what to do instead;
without that guidance, an absent dropdown option looks like a missing feature. The twin shape also
gained an end-to-end test. It imports an inline workflow with the framework fixture's topology and
checks its three relevant connections, but does not load the fixture file itself.

Reviewers also confirmed three assumptions:

- the `expect_failure` fixture with a retained `outputs:` block is conventional and correct;
  removing the block would let the test pass vacuously through a swallowed `KeyError`;
- the suspected tool-parameter false positive in `getDanglingGates` cannot occur because
  `step.inputs` is built with `connectable_only`; and
- every Selenium gate-mode label is byte-identical to its component label.

Three suggestions were deliberately deferred: collapse the dot and bracket fixtures, add a depth-2
nesting case, and rename `nogate` to `no_gate`. All are reasonable, but the plan specifies the
fixture inventory and naming, and none fixes a defect. They remain open items below.

## What still needs doing

1. **Land `optional_inputs` (#23333) first.** This branch is based on it, and the nested-bracket
   fixture asserts post-#23333 behavior.
2. **Address stale gate ports.** Typing a port from its source output means the port does not update
   when the *source* changes — remove `when` from the source step, or flip an output's optionality,
   and the downstream port keeps its old shape. `stepExtraInputs` is only recomputed for the step
   being written. The normal import order exercised by the E2E test does not reproduce a load-order
   failure: it imports a gated workflow and the marking clears. That does not prove arbitrary
   insertion order is safe. The fix is either a dependent scan on update or making
   `stepExtraInputs` a computed over `steps`; both are store restructures worth doing deliberately.
   Start in `client/src/stores/workflowStepStore.ts`, and make an upstream-only edit the first red
   regression so the test cannot pass through ordinary import order.
3. **Add coverage for the drop interaction.** `NodeInput.vue` has no Vitest today, and
   `workflow_editor_connect` does not work under Playwright. The terminal predicate is covered, but
   the confirmation dialog and undo grouping are not. Coverage needs either a new `NodeInput.vue`
   test or the Playwright drag helper described in the untracked
   `WORKFLOW_EDITOR_CONNECT_PLAYWRIGHT_PLAN.md` in the same worktree. The minimum regression should
   assert accept, cancel, custom-gate preservation, and one undo restoring both the connection and
   gate to their pre-drop state.
4. **Update training material.** The presence-gating pattern belongs in
   `galaxyproject/training-material`'s workflow-conditionals tutorial, which is a separate
   repository. Use `doc/source/dev/workflow_conditional_steps.md` as the Galaxy-side source of truth;
   Galaxy's own developer documentation already carries the content.

## Open questions raised during implementation

1. Should `isPathPrefix` match in both directions — should `$(inputs.cond ...)` answer for a
   connection named `cond|input1`? Currently no. Compatible with the plan's whole truth table either
   way; nobody writes it; left out deliberately.
2. The presence mode offers only connections whose value can be absent. Should it offer every
   connected input? Gating on a required input is harmless but pointless, and hiding the option when
   nothing qualifies is the clearer signal — but it does mean the mode silently disappears from the
   dropdown, which may read as a missing feature.
3. Is the confirm dialog the right response to a drop? It is the primitive the editor has and the one
   `Lint.vue` uses, but an inline offer on the connection would be less modal.
4. The `when` port keeps the boolean contract while every other probe is typed from its source. Is
   the reserved-name special case the right line, or should an integer probe under some other name
   also be refused?
