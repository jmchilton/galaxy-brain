# ExportForm

Selected originator: `client/src/components/Common/ExportForm.test.ts`. Baseline **7 tests** → final **7 tests**.

The shared `let wrapper: any` and its `beforeEach` mount are now a typed `mountExportForm(props)` factory. It drops the `as object` cast and the empty `props: {}`, and creates fresh `getLocalVue(true)` plugins for each mount. Wrappers unmount automatically. The three "export disabled" cases are now one `it.each` table that names which input is missing. A local `fillInputs` helper sets only the inputs a scenario provides, so the empty-both case still touches nothing. The button and name-input selectors and the two input values are named constants. Test names describe the behavior and the condition. The clear-after-export case passes `clearInputAfterExport` at mount instead of calling `setProps` afterwards.

All original assertions are kept, and some are tighter. Each old `exists().toBeTruthy()` is now `wrapper.get(...)`, which throws if the button is missing. `aria-disabled` truthy/falsy is now exactly `"true"` when disabled and absent when enabled, which is what GButton renders. The "not emitted before click" check stays. The `toHaveProperty("export")` + `emittedArg` + `emitted("export")[0][1]` trio became `toEqual([["gxfiles://", "export.tar.gz"]])`, so both arguments are still asserted and the test also proves exactly one emission. The clear case still asserts the button is disabled afterwards. It now also asserts that the export was emitted and that both the name input and FilesInput's `value` prop are back to `""`. Setting `clearInputAfterExport: false` in that test makes it fail on the name value. The localization check no longer needs `(expect(...) as any)` (see below).

`mount` stays. The assertions need the real GButton (`aria-disabled`, click handling, localized text) and the real BFormInput behind `#name`. FilesInput also renders for real. The test drives it by emitting `input`, as before. That works because `getLocalVue` already installs the router that FilesInput's `useRouter` needs.

Reuse: `getLocalVue` and `enableAutoUnmount`. The cast in the test had a comment saying custom matcher types weren't recognized with explicit vitest imports. The cause was two conflicting declaration files. `tests/vitest/matchers.d.ts` is a script file, so its `declare module "vitest"` was an ambient declaration rather than an augmentation. `types/vitest-setup.d.ts` redeclared `describe`/`it`/`expect` as `typeof import("vitest/dist/index.js")[...]`. Probes showed the matchers never merged. Probes also showed that making `matchers.d.ts` a module while `vitest-setup.d.ts` was present turned `expect` into `any`. Every test would then have lost its types while `vue-tsc` stayed green. Both files are replaced by one real module augmentation. The change is adopted in `ResetPassword.test.ts` and `RegisterForm.test.ts`. See `customMatcherTypes.md`.

Validation: ExportForm 7, ResetPassword 5 and RegisterForm 2 tests pass in shuffled order (seed `190101`, `NODE_OPTIONS=--no-webstorage`). Scoped ESLint (`--max-warnings 0`) and Prettier pass on all four changed files. Full `vue-tsc --noEmit` passes. One extra run included a temporary canary file, since deleted, to prove the types are real. `vue-tsc` reported exactly its four expected errors: `expect` and `describe` assigned to `number`, an unknown matcher, and `toBeLocalizationOf(3)`. The valid `toBeLocalizationOf`, `toBeLocalized` and asymmetric `expect.toBeLocalizationOf` calls compiled.

A repo-wide search found no other users of the matchers or the removed file: `src/`, `tests/`, `packages/` (whose tsconfigs include neither `types/` nor `tests/`) and the Tool Shed frontend.

Guidance: none.
