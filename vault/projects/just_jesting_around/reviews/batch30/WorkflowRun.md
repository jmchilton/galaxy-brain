# WorkflowRun

Selected originator: `client/src/components/Workflow/Run/WorkflowRun.test.js`. Baseline and final: **6 tests**.

Order bug found and fixed in the test. At HEAD the suite passes in file order but fails shuffled with seed `300101`: "loads run data ..." finds a tool step with `expanded === false`. `WorkflowRunModel` rewrites the run data's inputs in place (a `RuntimeValue` input becomes `null`), and the `getRunData` mock returned the same imported `run1.json` object every time. So whichever test built a model second saw the rewritten inputs, and that step no longer counted as open. The mock now returns `structuredClone(sampleRunData1)`, with a comment saying why. The fixture data is unchanged. The model's in-place rewrite is production behaviour that real API responses never hit, since each response is a fresh object, so it is noted, not changed.

Structure. The outer `beforeEach` mount, which the missing-tools helper had to `unmount()` to get its own Pinia (with a comment about Pinia re-activation), is replaced by one `mountWorkflowRun(props, initialState)` used by every case; missing-tools cases pass `REGISTERED_USER_STATE`. `mountWithMissingTools(props)` folds the repeated `mockRejectedValueOnce(new WorkflowMissingToolsError(...))` + mount + flush, and `triggerHistoryUpdate()` names the `lastUpdateTime` bump that re-runs `loadRun`. Fake timers and the mock's `setTimeout(0)` are gone: the loading state is visible synchronously after mount, and `flushPromises()` alone settles each load (the old `runAllTimersAsync` + `flushPromises` + `$nextTick` trio). The dead `vi.mock("app")` goes (nothing imports `app`). `resetMockConfig()` after each test stops the missing-tools config from leaking into the other cases under shuffle. Selector constants and auto-unmount are added.

`wrapper.vm` reads are replaced with what the template shows. Loading: the loading message. `workflowError === ""`: no `.alert-danger`. `workflowModel === null`: no WorkflowRunForm. `simpleForm === false`: WorkflowRunFormSimple absent. The parsed model is read from WorkflowRunForm's `model` prop, and all seven model assertions stay. The steps check was a `forEach` that would pass on an empty list; it is now an exact `[true, true, true, true, true]` for the five steps. The submission-error case no longer calls `vm.handleSubmissionError`. WorkflowRunForm emits `submissionError` instead, which is how the component receives it, and the test asserts the rendered "Workflow submission failed: Some exception here" alert text, not `vm.submissionError`. The pre-load checks in that case duplicated the first case's and live there. Added: the first case also checks `getRunData` was last called with `(workflowId, undefined, false)`, as its name says it loads from the API. The four missing-tools cases keep their assertions as they were.

`mount` stays: the assertions read GAlert, LoadingSpan and WorkflowMissingToolsRequest markup.

Reuse: `setMockConfig`/`resetMockConfig` from `@/composables/__mocks__/config`; no new shared helper. The sibling `WorkflowRunForm.test.ts` already copies the same fixture (`JSON.parse(JSON.stringify(sampleRunData1))`) before building its model, so the copy follows local precedent. `structuredClone` is the clearer spelling. `model.test.js` builds only one model from the shared object (its other case spreads in its own `steps`), so it is not exposed.

Validation, from `client/`: 6 tests pass shuffled with seed `300101` and with seeds 1, 2, 3, 7 and 8. ESLint (`--max-warnings 0`), Prettier and `vue-tsc --noEmit` pass.

Guidance: a JSON fixture imported into a test is one shared module object. If the code under test mutates what it is given, as `WorkflowRunModel` does, have the mock return `structuredClone(fixture)`, or the suite depends on test order. Only shuffled runs show it.
