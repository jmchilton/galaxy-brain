# summarize-nextflow resolver: on an ad-hoc DSL2 pipeline the workflow, params, tools, tuple outputs and license are wrong

- Target: galaxyproject/foundry. `packages/summarize-nextflow` is a Foundry package, and every defect is in its static resolver. No upstream tool is involved, and Nextflow was absent from the run. Foundry tracking needed: yes.
- Seen in: /home/ubuntu/foundry-runs/prose-nf2wb-callings-2026-10-29, phase 1 (summarize-nextflow), 2026-10-29. The ledger has 6 matching entries (`summarize-nextflow-*`).
- Existing issues/PRs: no duplicate. Related: #666 (open; workflow selection on nf-core/rnaseq, a different case), #466 (closed; IO naming, fixed `path name` but not quoted paths or continuations), #111 (closed; process discovery on ad-hoc layouts, the reason processes are found at all), #211 (open; names CalliNGS-NF for `from_param`), #176 (open; DSL1 posture).

## Symptom
On `CRG-CNAG/CalliNGS-NF@9e7ebf0` the output is schema-valid but mostly wrong. `workflow.name` is `UNKNOWN`, with 0 channels and 0 edges. `source.workflow` is `unknown` and the slug is `nextflow-unknown`. `params[]` and `tools[]` are empty, and the license is reported as `MIT`, though the repo is MPL-2.0. Each multi-line `tuple` output is split into 3-4 outputs with hash names (`output_967394812`). A warning says "no module process files found under modules/", even though all 11 processes were found in `modules.nf`. The LLM pass rewrote all of this by hand.

## Root cause
There are five independent causes, all in `packages/summarize-nextflow/src/resolver.ts` (package 0.4.0, worktree 0d8daf0e; the resolver is identical to origin/main 9f83fd55):
1. **The anonymous entrypoint is never parsed.** `parseWorkflows` skips unnamed blocks (`:1268 if (!block.name) continue;`), so `workflows` is empty and `primaryWorkflow` is null. Channels, edges and conditionals then fall back to `[]` (`:415-420`). The name comes from `parseWorkflowName` (`:613-617`), which defaults to `nextflow/unknown` when `manifest.name` is absent. `source.workflow` and `slug` are built from that name (`:388`, `:394`), never from the git remote or the repo basename. That breaks the schema's own slug rule ("repo basename otherwise"). The schema's `Workflow.name` description (`summary-nextflow.schema.json:347`) says an anonymous-only pipeline is "too small to summarize", so the contract also needs to change.
2. **Backslash-continued IO lines are not joined.** `parseIoBlock` (`:2102-2121`) splits the block on `\n` and makes one ChannelIO per line, so `tuple \` / `path(...), \` each become separate outputs. When an output has no bare identifier, `parseIoName` (`:2124-2132`) falls back to `${blockName}_${hash}`: quoted `path "${genome}.fai"`, or a continuation fragment. A one-line tuple is named after its first `val` (e.g. `replicateId`), which also misleads.
3. **Only JSON-schema and getGenomeAttribute params are read.** `parseParams` (`:848-916`) reads only `nextflow_schema.json` and `getGenomeAttribute` assignments. `source_kind: "params_block"` is declared (`:177`, schema `:100`) but never emitted anywhere. The same resolver already parses `nextflow.config` and entrypoint `params.X = ...` assignments for test candidates (`pipelineDefaultParams`, `:2592-2601`). Its output just never reaches `params[]`.
4. **Config-level containers are ignored.** `buildTools` (`:2172+`, called at `:349`) reads only per-process `container`/`conda` directives and `environment.yml`, so `process.container = '...'` in `nextflow.config` profiles is ignored. Even with Nextflow present, `mergeNextflowInspect` (`:452`) updates `processes[].container` after `tools[]` has been built, so `tools[]` stays empty. The modules/ warning (`buildWarnings`, `:457-467`) checks the path prefix `modules/` instead of whether any processes were found.
5. **License is hardcoded.** `:393` reads `license: existsSync(LICENSE) ? "MIT" : null`, and the file content is never read.

The ad-hoc cases in `test/resolver.test.ts` (egapx-shape, `:1183`) all have a named workflow and a `manifest.name`. In `content/molds/summarize-nextflow/scenarios.md`, the CalliNGS case (`:46-48`) asserts only "11 processes", and "ad-hoc DSL2 fallback" (`:158`) is still a placeholder.

## Proposed fix
One PR in the Foundry package, with synthetic regression tests for each cause and a CalliNGS-NF integration case:
1. When no named workflow exists, treat the entrypoint's anonymous block as primary: parse its calls, channels and edges, and keep the existing warning. Derive the fallback name and slug from `manifest.name`, then the remote repo basename, then the directory basename. Update schema `Workflow.name` to state the rule (the ledger's contract entry).
2. Join lines ending in `\` (and lines inside open parens) before splitting IO blocks. Name unnamed outputs positionally (`out0`, `out1`, or the emit index) instead of hashing. Don't name a tuple after its first `val`.
3. Emit `params[]` from `nextflow.config` `params {}` / `params.X =` (excluding profiles) and entrypoint `params.X =`. Use `source_kind: params_block` (or a new `script_assignment`), with `source_path`, `source_expression` and `default` filled.
4. Read config-level `process.container` (top level, `standard`/default profile, `withName`/`withLabel`) into `tools[]` with a warning that per-tool versions are unknown. Rebuild tools after the inspect merge. Fire the modules/ warning only when `processes.length === 0`.
5. Detect SPDX ids from the LICENSE / LICENSE.md / COPYING header (MIT, Apache-2.0, GPL-2.0/3.0, LGPL, MPL-2.0, BSD-2/3, AGPL). Otherwise emit `null` plus a warning.

## Draft issue
**Title:** summarize-nextflow: ad-hoc DSL2 pipeline gets UNKNOWN workflow, split tuple outputs, empty params/tools and hardcoded MIT license

On `CRG-CNAG/CalliNGS-NF@9e7ebf0` (no `nextflow_schema.json`, `meta.yml`, nf-test or `manifest.name`; processes in root `modules.nf`, DAG in an anonymous `workflow {}` in `main.nf`), `summarize-nextflow` 0.4.0 emits a schema-valid but mostly wrong summary. A pipeline run had to rewrite it by hand. Repro: `summarize-nextflow --no-with-nextflow workflow-fixtures/pipelines/CRG-CNAG__CalliNGS-NF`. The same causes show up on `nextflow-io/rnaseq-nf` and `ZuberLab/crispr-process-nf`.

Five independent causes in `packages/summarize-nextflow/src/resolver.ts`:
1. **Anonymous-only entrypoint dropped.** `parseWorkflows` skips unnamed blocks (`if (!block.name) continue;`), so `workflow` is `UNKNOWN` with 0 channels and 0 edges. `parseWorkflowName` defaults to `nextflow/unknown`, giving `source.workflow: unknown` and `slug: nextflow-unknown`, which breaks the schema's "repo basename otherwise" slug rule. Schema `Workflow.name` calls this case "too small to summarize". 11 processes and a `groupTuple` say otherwise.
2. **Multi-line IO split.** `parseIoBlock` splits on `\n`, so `tuple \` / `val(x), \` / `path(...)` become separate outputs. `parseIoName` hashes anything without a bare identifier (`path "${genome}.fai"` becomes `output_1566053798`).
3. **Script/config params ignored.** `parseParams` reads only `nextflow_schema.json` and `getGenomeAttribute`. `source_kind: params_block` is declared but never emitted, although `pipelineDefaultParams` already parses `params.X = ...` from `nextflow.config` and the entrypoint for test candidates.
4. **Config containers ignored.** `buildTools` reads only per-process directives, so `process.container` in `nextflow.config` yields `tools: []`. `mergeNextflowInspect` runs after `buildTools`. The "no module process files found under modules/" warning fires on a path prefix even when processes were found.
5. **License hardcoded:** `license: existsSync(LICENSE) ? "MIT" : null`. CalliNGS-NF and rnaseq-nf are MPL-2.0.

Expected: treat the anonymous entrypoint as primary when no named workflow exists, and name it from manifest, then remote, then directory basename. Join continued IO lines and name unnamed outputs positionally. Emit config/entrypoint params with `params_block` provenance. Resolve config-level containers into `tools[]`, and warn about modules/ only when no processes are found. Detect the SPDX id from the LICENSE text, or emit `null` with a warning.

Coverage gap: integration tests cover only nf-core fixtures, and the `summarize-nextflow` scenario for CalliNGS-NF asserts only the process count. Add a CalliNGS-NF integration case plus synthetic tests for each cause. Related: #666, #466, #111, #211.
