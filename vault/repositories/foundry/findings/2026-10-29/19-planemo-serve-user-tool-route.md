## Symptom
(a) Attempt 1 served an empty directory. Invoke returned 400: `the following required tools are not installed: Filter1 (version 1.1.1)`. The driver then copied `filtering.xml` and `filtering.py` into the served directory, and later attempts got past this.
(b) Attempt 4 ran with `TMPDIR=<run>/.scratch/serve-tmp`, a 100-character path. The upload's celery `fetch_data` task raised `OSError: AF_UNIX path too long`, followed by `BrokenProcessPool`. The upload job never reached a terminal state, and `planemo test` hung until it was killed after 1342 s. Attempt 5 used `TMPDIR=/var/tmp/cgt5` and passed.

## Root cause
(a) The empty-directory route is only a workaround for planemo#1757. Planemo puts Galaxy's stock ("distro") tools into its generated `tool_conf.xml` only for tool ids it reads from the runnables it serves or tests. It looks each id up in `DISTRO_TOOLS_ID_TO_PATH`, which has 112 entries, including Filter1, Cut1, cat1 and `__BUILD_LIST__`. With 0.75.47, any served or tested workflow that embeds a `GalaxyUserTool` crashes in that id scan, so the driver served nothing, and nothing triggered the distro lookup. This is documented planemo behavior (`--extra_tools` exists for exactly this), not a planemo bug. Planemo master already fixes the cause: it skips embedded tools in the scan and grants the managed user `user_tool_execute`. With it, a plain managed `planemo test wf.gxwf.yml` should get Filter1 automatically and need neither the role step nor the external route. #733 has the same gap but names only built-in *collection* tools, so it understates the scope. Confidence: high (read in source and reproduced in the 0.75.47 venv).

(b) CPython's forkserver puts its listener socket at `tempfile.gettempdir()/pymp-XXXXXXXX/listener-XXXXXXXX`. Galaxy's `override_tempdir` (default on) sets `tempfile.tempdir = new_file_path`, and planemo sets `new_file_path = <mkdtemp under $TMPDIR>/tmp`. Together these add about 48 characters to `$TMPDIR`. Here that made a 148-character socket path, well over the 107-character `sun_path` limit. Python 3.13+ and 3.14 fall back to `/tmp` when the path would be too long (gh-132124, gh-140734). Python 3.12 is security-only and never received that fix. On this host `/tmp` is a RAM-backed tmpfs, so a short on-disk `TMPDIR` is the right local rule. Not a Galaxy bug. Confidence: high.

(b′) The hang is Galaxy's own bug. The upload chain is `setup_fetch_data | fetch_data | set_job_metadata(link_error=finish_job) | finish_job`. `fetch_data` sets the job to RUNNING and then calls `abort_when_job_stops`. When that raises, no errback is attached to `fetch_data`, so the job stays RUNNING forever and clients poll indefinitely. Confidence: medium. The source read and the log agree, but it was not reproduced in isolation.

## Proposed fix
- **planemo:** close #1757 against #1763 and cut 0.75.48. No new planemo issue is needed. One optional nicety: `--galaxy_python_version` still offers only up to 3.12 on master (`options.py:192`). Allowing 3.13/3.14 would pick up CPython's fallback.
- **Foundry #733:** (1) Widen the built-in-tool caveat from collection tools to every `DISTRO_TOOLS_ID_TO_PATH` id. The workaround the run verified is to copy each stock tool's XML and helper script, taken from the served Galaxy's `tools/` directory, into the served directory, or to pass them with `--extra_tools`. (2) Gate step 2's exception on the planemo version: on a planemo with #1763 (≥0.75.48 or master), use the managed path and drop the role and serve recipe. Put both changes in #733 rather than a new Foundry issue. Keep #582 open until the release, then close it.
- **Foundry run-workflow-test (environment modality, ledger `run-workflow-test-no-resource-kill-modality`):** state that planemo puts the Galaxy root under `$TMPDIR`, and that on Python < 3.13 `$TMPDIR` must stay at or under about 59 characters. This is a doc line in the same Mold, not an upstream workaround.
- **Galaxy:** file the hang (draft below). Optionally, Galaxy could create the pool's socket directory outside `new_file_path`, but CPython already covers that on 3.13+.

## Draft issue(s)
**Repo:** galaxyproject/galaxy. **Title:** A `fetch_data` celery task that raises leaves the upload job RUNNING forever

The celery data-fetch chain (`lib/galaxy/tools/execute.py`, dev :405-424) attaches `link_error=finish_job` only to `set_job_metadata`. `fetch_data` (`celery/tasks.py`) moves the job to RUNNING and then submits to the forkserver pool. If the submission or the pool fails, the job is never failed. Seen on release_26.1 under planemo with a long `TMPDIR` on Python 3.12, where the pool raised `OSError: AF_UNIX path too long` and then `BrokenProcessPool`. The upload stayed RUNNING for 20 minutes until the client was killed. Expected: any exception in `setup_fetch_data` or `fetch_data` puts the job into `error`, with the exception in its info, for example by attaching the errback to the whole chain or by catching the exception in `fetch_data`. Repro: on Python 3.12, start Galaxy with `TMPDIR` set to a directory path of about 90 characters, then upload a file.

**Foundry comment on PR #733** (Foundry-owned, no upstream label): The callings v0 run (2026-10-29) hit the empty-directory serve gap with stock `Filter1`, not just collection tools. Planemo only adds `DISTRO_TOOLS_ID_TO_PATH` tools for ids in the served target. Staging `stats/filtering.xml` and `filtering.py` into the served directory fixed it. Please widen the caveat to every distro tool. planemo#1763 (merged 2026-10-29, unreleased) fixes #1757 and grants the role, so once 0.75.48 ships, step 2's exception should switch back to the managed path.
