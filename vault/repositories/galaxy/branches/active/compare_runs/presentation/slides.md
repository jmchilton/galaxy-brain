# Compare runs in Galaxy

- **Audience:** Galaxy users: clients, scientists and research groups who run the same workflows and tools again and again.
- **Length:** 13 main slides, about 13 minutes. Extra slides follow the divider and aren't part of the time budget.
- **Takeaway:** Galaxy can now line up every run of a workflow step, a workflow's outputs or a tool in one table, across workflow versions, and show what changed and why.
- **Demo data:** one "Exon selection" workflow run on CCDS and RefSeq coding-exon BED files across three versions. v2 relaxed the filter from `c3-c2>=200` to `c3-c2>=100`; v3 changed how many top exons it keeps. A batch copy maps over a list and reuses cached jobs, and a nested copy puts the filter inside a subworkflow.

Fix 2 changes what slide 4 shows: without it the changed parameter isn't highlighted. Fix 1 only lets comparison pages open without Galaxy's side panels, which is how slides 5, 7, 9, 10 and 11 and extras E1–E3 were captured. Without it those pages still work, with the panels showing.

## 12. Known gaps

- **Steps inside a subworkflow** can't be compared across runs yet. Their All runs tab says so and points to the parent run.
- **Unlabelled steps and outputs** can't be compared, because labels are how runs are matched across versions.
- **Output datasets** are compared by their metadata, such as line counts, not by their contents.
- **The tool form** has no "previous runs" panel yet. Start from a job or a dataset instead.

> Notes: Here is what it doesn't do yet. The subworkflow case says so plainly, rather than showing a table that would mislead. The practical advice is to label the steps and outputs you care about and keep those labels stable. I'd like to hear which of these gaps would get in your way.

## E4. The API behind it

Three read-only GET endpoints, one shared table format.

- `/api/workflows/{workflow_id}/step_runs?step_label=…`: every run of one labelled step (mode 1). Optional `versions`, 0-based and repeated for several.
- `/api/workflows/{workflow_id}/output_runs`: labelled inputs and outputs of every run (mode 2). Optional `output_labels` and `versions`.
- `/api/tool_runs?tool_id=…`: every submission of a tool, across versions (mode 3). Optional `tool_versions`, `history_id` and `include_workflow_jobs` (on by default).
- All three also take `limit` (default 25), `offset`, `sort_by` and `sort_desc` (newest first by default), `states` and `metadata_elements`. The total count comes back in a `total_matches` header.
- The page `/comparisons?kind=step_runs|output_runs|tool_runs&…` takes the same keys, so every entry point links to a pre-filled page.

> Notes: All three return the same table: columns for inputs and outputs, one row per run, restricted to the caller's own runs. `workflow_id` is the workflow's id, or a single version's id with `instance=true`. Because they are plain GET requests, the same comparisons can be scripted with any HTTP client. No database migration is needed.
>
> [Sources] Verified against the code at `be7415d94dd`: `lib/galaxy/webapps/galaxy/api/comparisons.py` (routes, query parameters, `total_matches` header), `lib/galaxy/schema/comparisons.py` (`COMPARISON_LIMIT_DEFAULT = 25`), `lib/galaxy/webapps/galaxy/services/comparisons.py` (caller's user id; anonymous callers get an empty table), `client/src/components/Comparison/comparisonQuery.ts` (`/comparisons` keys per kind). 0-based `versions`: `design_questions.md` Q19. No migration: `../index.md`; the branch's only model change adds a dict key.

## E5. What the export contains

- The current page, as CSV or TSV, with the columns you've chosen, in transposed form if the table is transposed.
- Datasets as `hid: name`, values as one-line JSON, metadata (such as line counts) as its value, missing cells as their text, such as "not run yet".
- Spreadsheet-safe: cells that start with `=`, `+`, `-` or `@` get a leading `'`, so Excel doesn't run them as formulas. CSV starts with a UTF-8 byte-order mark so Excel reads non-ASCII names.

> Notes: The export is built in the browser from what the table displays, so it matches the screen.
>
> [Sources] `subagents/phase_5_implementation.md` ("3. CSV/TSV export"). `subagents/phase_5_review_fixes.md` (item 1, `spreadsheetSafe`; UTF-8 BOM). `implementation_debrief.md` ("CSV/TSV export with spreadsheet-safe cells").

## E6. How runs are matched across versions

- **Steps** are matched by their label. An unlabelled step can't be compared, and renaming a label starts a new history for that step.
- **Workflow outputs and inputs** are matched by label. Columns only older versions have are placed last.
- **Tool runs** span tool versions, with a version column and filter.
- Labels were chosen over internal step ids because ids change on edits and imports, while labels are visible and under your control.

> Notes: This is the design choice most likely to affect users: label the steps and outputs you care about, and keep the labels stable.
>
> [Sources] `plan.md` ("Matching across versions"; "Alternative Approaches": matching by uuid).

- Steps inside subworkflows can't be compared yet; the tab above says so and points to the parent run. An unlabelled step's tab asks you to label it.
- Unlabelled outputs can't be compared either.
- Output links are never highlighted as "different", because every run makes new datasets; compare them by line count or another metadata value instead.
- Row links open the run; jumping straight to the same step needs a separate Galaxy change, #24173.
- Wide tables scroll sideways on a 1280 px screen, and the parameter diff in a row's detail is readable but tall.
- In mode 1, a version none of whose runs recorded outputs is assumed to have every output on the page.

**Focus:** the open "All runs" tab and the blue message under it.

> Notes: None of these blocks the main use, but they are worth knowing before a demo on your own data.
