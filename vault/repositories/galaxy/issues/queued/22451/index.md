# galaxy#22451 — Exception: Failed to extract job.

[Issue](https://github.com/galaxyproject/galaxy/issues/22451)

Branch `issue_22451_extract_job_errors` — Sentry `Exception: Failed to extract job.` from workflow extraction. **Error handling only — the underlying condition is not fixed and the report is deliberately kept firing.** Both untyped raises in `extract_steps` put their whole diagnostic in a `log.warning` and threw something with no job, tool or output name in it. State: one commit `06852c35b74` on `origin/release_26.1` `bc71722b3ae` (2026-09-22), pushed to `jmchilton`, **no PR**. (1) A `job_id` missing from `job_id2representative_job` raised `AssertionError("Attempt to create workflow with job not connected to current history")` — a cause it never checked: the commonest way to drop out of the summary is `_check_state` skipping an output still `new`/`queued`/`running`, which already records `WARNING_SOME_DATASETS_NOT_READY`; now a 400 naming the *encoded* job id and appending that explanation when the warning is set. (2) A map-over output matching no implicit collection raised bare `Exception("Failed to extract job.")`; now `InconsistentApplicationState` (500) naming job id, tool, the unplaceable output and the collections that were found. **Sentry trap caught in review:** Galaxy captures only through `LoggingIntegration(event_level=ERROR)` — `add_sentry_middleware` is defined in `webapps/base/api.py` but never called — and a `MessageException` is *handled* (logged at INFO by `message_exception_middleware`, not at all by the legacy `decorators.py` path), so converting the bare `Exception` would have silently closed #22451; the log record beside the raise is therefore `log.error` with lazy `%s` args so the event still fires, groups on the format string and carries the raw pairs. Lookup extracted to `_implicit_map_output_hid()`; its `__new_primary_file_` prefix alternative was unreachable from the day it was written (the `continue` predates the helper, see `424f70391ec^`). Covered by one API test, `TestWorkflowExtractionApi::test_extract_job_without_summarized_output_rejected` (tool run in history A, extract from history B with A's job id), verified red first against unmodified `extract.py` where it reproduces the issue exactly — 500 `Uncaught exception in exposed API method:`. Path (2) and the not-ready message suffix are untested: (2) has no known API-level recipe (that is the condition this PR exists to diagnose) and the not-ready case is a race. `test_workflow_extraction.py` API 48 passed 1 skipped, `test/unit/workflows/` 108 passed 1 skipped, `make mypy` 19 errors = the unmodified base's 19, pre-commit clean. `release_26.0` has the same two raises at `:138`/`:187` but the file has diverged too far to cherry-pick. PR description in `vault/agents/gx_branches/issue_22451_extract_job_errors_pr_description.md`. **Open:** the root cause — untested candidates are the per-collection `creating_job_associations[0]` representative-job pick disagreeing across a multi-output mapped tool, and a mapped tool with a collection output never landing in `implicit_map_jobs` because the inner per-element HDCA is summarized first; both belong to [#22709](https://github.com/galaxyproject/galaxy/issues/22709). Also open: whether an unplaceable output should warn and drop the connection rather than fail the whole extraction (probably the better answer for the still-running case, but a behaviour change), and whether the not-ready 400 wants `ToolInputsNotReadyException` plus `retry_after` instead.
