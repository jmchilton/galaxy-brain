# Raw: Pulsar `none` + `remote_metadata: true` never runs set_meta

Found by gx_workhorse while implementing #24600 (branch `issue_24600_pulsar_none_extra_files_25.1`, base release_25.1 32317280ecb, `pulsar-galaxy-lib` as pinned on 25.1). Not security-relevant.

## Symptom

`test/integration/embedded_pulsar_none_job_conf.yml` (used by `test_pulsar_embedded_none.py`, added for #21566 / PR #21578) sets `remote_metadata: true` and `default_file_action: none`. Every job run there ends with:

- job stderr: `python: can't open file '<galaxy tmp>/database/pulsar_staging/<job id>/metadata/set.py': [Errno 2] No such file or directory`
- handler log: `galaxy.metadata WARNING ... setting metadata externally failed for HistoryDatasetAssociation N: External set_meta() not called`
- the job still ends `ok`, exit code 0, outputs keep whatever metadata they had at creation.

Seen for `simple_constructs` (test passes anyway; its assertions don't touch metadata) and `composite_output_tests` (test FAILS: velvet's primary `output.html` is regenerated by `set_meta`, so the expected "Velveth dataset:" html never gets written and the test sees the default composite html).

## Why (inferred from code, not stepped through)

- Galaxy (`lib/galaxy/jobs/runners/pulsar.py`, `queue_job`) passes `metadata_directory=<job working dir>/metadata` in `ClientJobDescription`.
- `__build_metadata_configuration` with `remote_metadata` points the metadata command at `remote_job_config["metadata_directory"]` (the Pulsar staging dir's `metadata/`).
- Pulsar `client/staging/up.py` `__upload_metadata_directory_files` → `transfer_tracker.handle_transfer_directory(path_type.METADATA, ...)`; the action for those paths under `default_file_action: none` has `staging_needed == False`, so nothing is copied. Remote `metadata/set.py` never exists.
- So with `none` the metadata command should either reference Galaxy's local metadata dir (shared FS), or the metadata dir should always be staged/rewritten regardless of the default action.

## Questions for research

- Is this also on dev / 26.x? (Not checked; dev has many metadata/pulsar changes: "Containerized set metadata" ecd065dd34c, "Move metadata handling into finish_job" 06e1864a13a.) `composite_output_tests` passes on `release_26.2` at `10ffdf8c742` under this same `none` + `remote_metadata: true` conf (2026-11-05), so the symptom above may be stale there; re-check before filing. Cause not investigated.
- Does `remote_metadata: false` + `none` work (Galaxy sets metadata locally after the job)? Likely the safer config for shared FS; the `none` integration test config may have meant to cover that.
- Is `remote_metadata: true` + `none` a supported combination at all? If not, Galaxy should warn/fail at config time rather than silently skip metadata.

## Same root shape, second symptom: `$__tool_directory__`

Same run: `markdown_report_extra_files` under `default_file_action: none` fails with `cp: cannot stat '<galaxy tmp>/database/pulsar_staging/<job id>/tool_files/data/1.bed'`. The command line's `$__tool_directory__` is rewritten to Pulsar's `tool_files` staging dir, but under `none` the tool files are never copied there. Possibly a separate issue (tool dir rewrite vs. metadata dir rewrite), but both are "Pulsar rewrites a job-directory path to its staging dir, then `none` skips staging". Worth checking whether `remote_metadata: false` changes this one (it shouldn't).
