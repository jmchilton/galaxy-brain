## Current implementation and earlier concern

The older regex-only implementation is gone. Unknown-extension normalization now runs on the job's dataset and library outputs at finish, after post-job actions and tool hooks, and in the failure path. It propagates to associations of the same underlying dataset with the same extension, while preserving copies that have deliberately been retyped. This addresses John's objection to treating regex captures differently from declared output formats and tool-provided metadata.

The shared `resolve_discovered_extension` resolves explicit `_sniff_` and `_infer_from_file_name_` tokens in both primary-dataset discovery and dynamic collection population. Pattern-captured extensions still take precedence. Compressed sniffing uses `auto_decompress=False`, consistent with storing the discovered bytes unchanged. XML docs and the linter recognize these tokens. The additional warning message has matching Python and generated/client schema entries and reports the original extension. The `format="input"` framework expectation changes reflect the new normalization policy, rather than weakening an unrelated test.

John's October 10 reply accepts `data` if applied uniformly, and his earlier reply explicitly permits dropping a profile gate. The lack of a profile gate is therefore not raised as an unresolved blocker. The prior request-changes tracking reflected the earlier special-case implementation; this review supersedes it for the commit above.

A real framework tool that discovers a dotless `README` with `(?P<name>[^.]+)\.?(?P<ext>.*)` finishes successfully, but its element has `extension=""` / `file_ext=""`, with `Data` as the resolved datatype. A regression expecting `data` fails. This is the same persisted-extension-versus-resolved-datatype inconsistency for an empty suffix, although it predates this revision. Consider normalizing empty strings too and retaining a dotless-file regression. This review does not claim the empty extension blocks downstream collection jobs.

**P3 — The `auto` exemption is not limited to deferred outputs** (same lines). The comment and PR body describe a deferred-materialization exception, but the condition skips every `auto` extension. A normal discovered collection using `pattern="__name__" format="auto"` finishes in state `ok` with extension `auto`; the element is not deferred. A regression expecting `data` fails. Consider checking the deferred state when granting this exemption, or explicitly documenting that all unresolved `auto` outputs are exempt. This is a retained legacy gap, not a demonstrated new execution regression: an independent downstream `data_collection` consumer successfully completed with that output. An anticipated downstream rejection was disproved by the runtime probe and is not a finding.

Both regression assertions pass with an isolated in-memory replacement of the guard that normalizes empty strings and exempts `auto` only for `Dataset.states.DEFERRED`. No Galaxy source files were edited. The original submitted framework fixtures pass on unchanged HEAD.

## Risks

The new sniff/infer tokens and finish-time fallback establish tool/workflow behavior that users will depend on, so this has compatibility risks beyond a mechanical refactor.

<details><summary>Risk Details</summary>

- All tool profiles now downgrade unregistered output extensions to `data`; the original extension is retained in the job warning, but installing that datatype later will not automatically retype those datasets.
- Explicit `_sniff_` and `_infer_from_file_name_` become discovery contracts, including compressed-byte behavior and the priority of captured extensions.
- Modern tools that produce the literal `input` format now get `data`; legacy profile behavior is preserved separately.
- Copies with the same unregistered extension are retyped along with the output. Deliberately retyped copies are preserved.
- The new `unknown_datatype` job-message variant adds a public API shape; consumers should tolerate the additional message type.

</details>

The persistent extension changes and new discovery tokens deserve deliberate compatibility review; no database migration is introduced.
