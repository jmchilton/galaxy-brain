## Finding

**P2 — Keep connected conditional discriminators serializable during extraction.**

Location: `lib/galaxy/workflow/extract.py:174–177`.

When an expression output feeds a conditional's **select discriminator**, the new callback replaces the recorded option with `ConnectedValue()`. `visit_input_values` then recomputes the active case from that marker, and `Conditional.value_to_basic` repeats that computation during `params_to_strings`. A marker matches none of the select's options, so extraction raises `ValueError: No case matched value` and returns HTTP 500. This applies to both history/HID and ID-based extraction.

This is an introduced extraction regression, separate from an existing workflow-import problem with connected select discriminators. The API reproduction seeds the ordinary persisted connection used by workflows saved before the independent September 28 ConnectedValue-on-import change, calls `attach_ordered_steps`, and invokes the saved workflow through the real API with the existing `allow_tool_state_corrections` option. The source workflow completes successfully with every job `ok`: `param_value_from_file` reads `default` and feeds `output_filter_exception_1/options|options`. Selecting both jobs returns 500 in both extraction endpoints at this PR's HEAD. Disabling only the newly added `_connect_parameter_inputs` pass on the same invocation returns 200 for both endpoints.

Please preserve a concrete discriminator through conditional traversal/serialization, or make the conditional handling explicitly support the marker without losing the branch. Add coverage where the discriminator itself is connected; the current conditional unit case keeps its selector literal and connects only its child text parameter.

Evidence: [API reproduction](test_saved_conditional_selector.py), [sanitized output](reproduction-output.txt).

## Implementation and coverage

The overall design is appropriate: one shared second pass for both extraction APIs, using `Job.effective_workflow_invocation_step` so mapped jobs use the existing abstraction. Keys include both invocation ID and original workflow-step ID. Building all sources before walking consumers makes parameter wiring independent of selection order. The callback avoids dataset/collection parameters, preserves already-created connections, and does not add a partial connection set when a source was omitted.

The submitted unit tests check ordinary, repeat and conditional-child parameters, omitted sources, different invocations, reverse selection order and standalone jobs. They do not weaken existing tests. Imports are at module scope. The two submitted API tests already exercise the useful end-to-end path: run a workflow, extract it through each endpoint, inspect both parameter edges, reimport it, change the input, and confirm that the final dataset is recomputed.

## Risks

The code is reversible, but extracted workflow files persist the restored dependency behavior and can be exported to other servers, so incorrect connections have an artifact-level one-way risk.

<details><summary>Risk Details</summary>

- Extraction now changes recorded parameter constants into runtime connections when the selected source shares an invocation; source matching must remain strict to avoid joining unrelated runs.
- Group traversal and serialization must preserve conditional/repeat structure and the recorded value when the source is absent. Connected conditional select discriminators currently make extraction fail, as reproduced above.
- Workflow artifacts already exported cannot be corrected merely by rolling back the server code; users would need to extract them again.
- The patch does not change API signatures, introduce a database migration or modify the originating history/jobs. Ordinary dataset wiring remains in the existing extraction pass.

</details>
