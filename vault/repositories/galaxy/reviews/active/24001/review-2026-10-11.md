## Implementation and surrounding behavior

The scalar branch of `ToolEvaluator._deferred_objects` previously unconditionally materialized a deferred dataset, while the multiple-data branch honored `allow_uri_if_protocol`. This change uses the existing predicate for scalar data parameters as well. Passing the actual parameter obtained by `visit_input_values` also makes policy lookup correct for inputs inside sections, conditionals, and repeats, where `self.tool.inputs.get(prefixed_name)` cannot find the nested parameter.

The new `uri_inputs` set is necessary: the later flat `input_datasets` scan must not rediscover and materialize an allowed scalar URI under its prefixed name. Inputs without a matching protocol still enter the materialization map. `DatasetFilenameWrapper._path_or_uri` already renders an unmaterialized dataset's source URI, so no additional wrapper behavior or URI syntax is introduced.

I checked dataset collection handling, multiple-data reduction, the standard input visitor, `DefaultToolAction.collect_input_datasets`, parameter replacement, and wrapper path rendering. Collection materialization and the legacy flattened multiple-input/Pulsar fallback remain intact. The fallback still does its older top-level lookup for unmatched numbered aliases; broader nested multiple-input policy support is not established by this patch and is not a newly introduced regression.

## Risks

Risks are low and the implementation is easy to revert; it restores an existing tool declaration's behavior without introducing a new artifact or API format.

<details><summary>Risk Details</summary>

- Tools declaring `allow_uri_if_protocol` now receive the permitted URI for scalar inputs, including nested ones. Such tools must actually support that URI from their compute environment; this is the existing declaration's contract.
- Unmatched protocols and tools that do not opt in must continue receiving materialized files; the new control test covers that boundary.
- The job-preparation change touches shared deferred-input machinery, but surrounding evaluator/materializer and existing collection tests passed.
- Real remote runners and every supported release/backport combination were not exercised locally. Legacy flattened multiple-input handling remains a separate limitation.

</details>
