## Findings

### P2 — Clear persisted store_root when normalizing a previously created Zarr dataset

At `lib/galaxy/metadata/set_metadata.py:157–160` and the removal of the Zarr `store_root` spec in `lib/galaxy/datatypes/data.py:1344`, the new grooming step moves the contents of an existing wrapped store to the root, but does not clear its previously persisted `store_root`. `MetadataCollection.__getattr__` continues to return unknown keys in the HDA's `_metadata`. Portable metadata serialization omits unknown keys; its loader only removes missing keys in the current metadata spec, so removing the spec does not remove the old stored value.

This breaks the published `$input.extra_files_path/$input.metadata.store_root` pattern after metadata reset: it resolves to the deleted wrapper directory rather than the normalized root. This is different from the disclosed limitation of leaving old data unnormalized.

A normal API reset was verified with a historical-layout HDA (`extension=zarr`, `store_root=wrapped.zarr`). The metadata job completed successfully, `.zgroup` moved to the root, and the DB still held `store_root=wrapped.zarr`. Running the PR's own `zarr_store_root_compat` consumer then produced an error with `ls: .../wrapped.zarr: No such file or directory`. The current compatibility test only covers newly staged data with no old metadata.

Ensure the obsolete value is cleared on the persisted association when normalization succeeds, including the portable metadata reload path. Add an API regression using an HDA carrying the historical field, reset metadata, then consume it through the published XML pattern. Avoid clearing the value while leaving an old wrapped layout in place.

Evidence: [real-model probe](legacy-metadata-probe.py), [API reset diagnostic](test_legacy_reset.py), [validation evidence](validation-evidence.txt).

### P2 — Include the current implicit-conversion fix, not its earlier cherry-pick

An independent end-to-end YAML fixture produces `formats: fasta fasta` and raw FASTA in the tabular output; its expected identifier assertion fails. Distinct input/output names and strict history checks avoid the separate fixture issue from the current #24004 review.

The underlying shared-input problem also exists on the base; this is an incomplete dependency fix carried by this PR, rather than a new regression introduced by directory runtime support. Bring in the current format-aware fix with a working shared-input fixture. #24004's Python 3.8 aliases and fixture collision are separate issues on that later head, and were **not** attributed to this earlier cherry-pick.

Evidence: [real-model probe](shared-input-probe.py), [independent fixture](shared-input.yml), [framework runner](run-shared-framework.py), [validation evidence](validation-evidence.txt).

## Risks

This has one-way compatibility risks: it changes persistent directory layout, removes a serialized metadata field, and establishes the YAML directory input contract.

<details><summary>Risk Details</summary>

- Normalization physically renames store contents. Rolling back code does not restore removed wrapper directories.
- Old histories and history exports can retain wrapped stores; root-only reads and omitted `metadata_store_root` lose preview/viewer compatibility.
- Historical HDA metadata can outlive the datatype spec and interact with published XML wrapper templates, as reproduced above.
- YAML directory `path` now means rewritten extra-files content rather than the empty primary file. Collection/conversion and distributed staging must preserve that representation.
- Cloud storage caches and remote materialization need the same root rule; current local tests do not prove cache eviction or mixed-deployment behavior.
- Vizarr must ship alongside the matching pin before the field removal reaches users.

</details>

<details><summary>Risk Review Advice</summary>

Decide explicitly whether existing Zarr histories and published tools retain compatible reads, migrate once, or require an operator recovery procedure. Exercise a previously created wrapped store through metadata reset and a published XML consumer, and verify the Vizarr pin in the final diff.

When combining the remote-directory work, cover wrapped content before persistence plus a subsequent rematerialization/cache miss. The existing API, metadata integration, embedded Pulsar, and object-store test harnesses provide the building blocks; no new browser framework is required.

</details>
