## Behavior and implementation

The layout picker is a small pure helper. GCard measures the header and actual badge/indicator children, preserves the previous layout while hidden, coalesces class updates into an animation frame, and cancels pending frames on unmount. The pinned VueUse `useResizeObserver` disconnects and stops its post-flush watcher on scope disposal. These lifecycle paths are consistent with surrounding composable usage.

The actual component and production styles were exercised in Chromium with small badges, the real HistoryDatasetsBadge component (its counts request fulfilled by the harness), and multiple badges. Across 17 HEAD width samples from 220 to 1000 pixels, the caret stayed inside the header on the first row. The pre-PR component reproduced clipping with the same wide history badge. Inline, column and stacked layouts switched as expected; a stable header produced no further class mutations during the one-second observation. Badge replacement, controls removal, component remounting and a 150% root font size worked without browser page errors.

The real dropdown opened and raised the card's existing overflow/stacking classes. The keyboard sequence was checkbox, title link, rename, badge, bookmark, dropdown toggle. This matches the PR's documented intentional change. In stacked/column layouts, badges remain earlier in DOM/tab order despite appearing below the actions; that acknowledged design choice is not a new finding. Event handlers, menu wiring, content sanitization, descriptions, footers and IDs outside the changed grouping are preserved. Existing ToolsList, PageCard, CuratedWorkflowCard and WorkflowCardList suites passed alongside the changed component/layout tests.

## Limits and nonblocking observations

A single very wide HistoryDatasetsBadge still clips when its natural width exceeds the entire card (the tested 220–300px cards). Wrapping the new badge *group* does not wrap the contents of that existing single pill. The same pill clips on the exact pre-PR component; the new header still fixes its caret and title placement. Treat this as a residual preexisting limitation, not a regression or an approval blocker. Ordinary multiple badge pills wrap correctly.

The browser harness renders production GCard, dropdown, controls, badges and styles but does not run a Galaxy server or exercise every consumer end to end. Its tooltip and sanitization directives are no-ops, so it provides layout and control evidence rather than tooltip/security validation. Chromium only was tested locally; GitHub's broader client, lint, build, Selenium and Playwright checks succeeded. No check artifacts were available locally, so no artifact-specific claims are made.

## Risks

Risks are minimal: this is a reversible UI layout change, with no persisted data, API or workflow/tool contract change (a two-way door).

The shared GCard has many consumers, so the meaningful remaining risk is a layout or accessibility regression in an unusual combination of slots, long content or header controls. The focused real-browser checks and sibling suites reduce that risk; the documented tab order change deserves human acceptance. Rollback restores the old layout without requiring a migration.
