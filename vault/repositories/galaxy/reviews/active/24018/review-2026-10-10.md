## Findings

### 1. P1 — Separately installed foreign requirements do not stay active together

[resolvers/conda.py:443](https://github.com/galaxyproject/galaxy/blob/0adbdb6655216e7a04c3d9e47816d3f06747fc31/lib/galaxy/tool_util/deps/resolvers/conda.py#L443)

When a tool needs two packages whose individual foreign copies exist but whose merged foreign environment does not, `resolve_all` returns empty and `resolve` returns a `MergedCondaDependency` pointing at each individual environment. `dependency_shell_commands` then sources the activation script for each environment in succession. Ordinary Conda activation replaces the previously activated environment's PATH instead of stacking environments. The job therefore loses the earlier requirement despite both resolving successfully.

This state is accepted by `_platform_has_targets`, which falls back to checking every individual environment; the platform routing helper can consequently choose the foreign destination. It can arise after individually installing packages or backfilling a pre-existing collection of single-package environments. The pre-submission check also passes because every requirement has a non-null dependency.

**Reproduction:** installed the fake `samtools=1.0` and `bwa=1.0` environments separately, then used the real routing and dependency resolution methods for a tool requiring both. Available platforms included `linux-aarch64`; routing chose `arm`. Both requirements became individual `MergedCondaDependency` objects. Executing their emitted shell fragments with actual Conda activation and tiny shell executables yielded `samtools: command not found` (127), while `bwa` succeeded (0). The activation script was substituted with the installed native Conda script to execute the shell semantics locally; this was not a foreign-hardware job.

Use a combined environment for the requested platform, or otherwise guarantee compatible simultaneous resolution. Availability/routing must agree with the environment that can actually be activated. The existing native individual fallback builds or augments the same job-specific isolated environment; the new foreign fallback does not preserve that behavior.

### 2. P2 — The second resolution drops the tool installation context

[jobs/__init__.py:1209](https://github.com/galaxyproject/galaxy/blob/0adbdb6655216e7a04c3d9e47816d3f06747fc31/lib/galaxy/jobs/__init__.py#L1209)

`Tool.build_dependency_shell_commands` resolves with `installed_tool_dependencies`, `tool_dir`, `job_directory`, `preserve_python_environment`, `metadata`, and `tool_instance`. `_check_platform_dependencies` repeats resolution with only `platform` and `return_null`. Resolvers whose answer depends on the tool installation, particularly `ToolShedPackageDependencyResolver`, therefore give different answers to these two calls.

**Reproduction:** with the real Tool Shed resolver and a valid installed `bwa=1.0` dependency directory, the real tool method generated a PATH activation command. The wrapper with an explicitly native `platform: linux-64` then raised `PlatformDependencyError` claiming the same requirement was missing. A Conda resolver configured for multiple platforms was present, so the native/foreign distinction was resolved normally.

Reuse the actual resolution result, or factor out one resolution method that preserves the same context for command generation and validation. An explicitly native platform must retain the resolver-chain behavior of the ordinary native path.

### 3. P2 — Enabling containers is not proof this job uses one

[jobs/__init__.py:1203](https://github.com/galaxyproject/galaxy/blob/0adbdb6655216e7a04c3d9e47816d3f06747fc31/lib/galaxy/jobs/__init__.py#L1203)

`_destination_runs_container` checks only `docker_enabled` / `singularity_enabled`. Those flags allow a container runtime; they do not guarantee that container resolution found an image for this tool. `BaseJobRunner.build_command_line` can receive no container and continue unless the tool requires containerization. A destination with Docker enabled can therefore run a bare job, yet the new platform guard skips its missing requirements and emits an empty dependency command list. A selected container with `resolve_dependencies` also still needs dependency resolution.

**Reproduction:** the real wrapper property for an unresolved `bwa=1.0` foreign requirement returned `[]` without an error when only `docker_enabled: true` was set.

Use the actual selected container to decide whether dependency validation is necessary. `command_factory.build_command` already suppresses dependency generation for containers that provide their dependencies, and invokes it for bare jobs or containers requesting dependency resolution. Removing the flags-only exemption from this property fits that existing distinction. Include a runner-level regression test where Docker is enabled and container lookup returns no image.

### 4. P2 — A job-metrics package test now imports the Galaxy application

[test_core.py:13](https://github.com/galaxyproject/galaxy/blob/0adbdb6655216e7a04c3d9e47816d3f06747fc31/test/unit/job_metrics/test_core.py#L13)

These tests are reused in standalone `galaxy-job-metrics` package testing. The added top-level `from galaxy.jobs import MinimalJobWrapper` imports an application module absent from that package, whose dependency is `galaxy-util`. CI package testing stops during collection with `ModuleNotFoundError: No module named 'galaxy.jobs'`, also affecting `test_env.py` because it imports `_run_plugin` from this module.

Move the wrapper mismatch-warning tests into `test/unit/app/jobs/`; keep the metrics plugin tests within the standalone package's dependency boundary. Actual package CI logs demonstrate this failure on both Python 3.10 and 3.14; it is not a missing local development dependency.

### 5. P2 — Fake executable fixtures are not portable to the CI checkout or macOS

[test_conda_multiplatform.py:109](https://github.com/galaxyproject/galaxy/blob/0adbdb6655216e7a04c3d9e47816d3f06747fc31/test/unit/tool_util/test_conda_multiplatform.py#L109)

The fake Conda and signer scripts embed `sys.executable` directly in a shebang. Unit CI runs from the `galaxy root` checkout, putting a space in the virtualenv interpreter path. The operating system splits that shebang and cannot execute the script, resulting in `FileNotFoundError` for the existing fake executable. Both unit artifacts report 42 failures, all in this new file, with this initial failure cascading into resolver/backfill assertions. A local minimal probe with a Python interpreter symlink under a directory containing a space reproduces the same error.

Separately, several fixtures hardcode `codesign_exec="/bin/true"`. On this macOS host `true` is `/usr/bin/true`; three otherwise focused tests fail because `/bin/true` does not exist. The PR explicitly supports macOS and the unit tests should not require a Linux-specific executable location.

Invoke Python explicitly or use a portable wrapper that quotes the interpreter path; reuse `FakeSigner` rather than a hardcoded `true` path. These are fixture failures, not evidence that 42 separate production behaviors fail.

## Coverage and design advice

The fake executable suite covers the filesystem/marker/locking machinery extensively, and the routing and wrapper units cover their branch decisions. These boundaries miss whether a generated command can actually run every declared requirement. A focused integration test should configure a fake platform-aware prefix with separately installed requirements, submit a small tool using both commands through a real runner, and verify that routing, preparation and shell execution agree. A second case should use an explicitly native destination with a contextual resolver; a third should enable Docker but return no image. These can use local fixtures and shell tools without a heterogeneous cluster. Actual foreign binaries, NFS cross-host locking, and macOS re-signing still need the author's real test rig.

Reuse a single contextual dependency resolution result for checking and command generation, and make platform availability reflect actual runnable environments. Those abstractions would prevent the readiness and execution paths from drifting.

## Risks

The main one-way risk is establishing administrator configuration and dependency-resolution behavior for heterogeneous destinations, including which combinations of declared tool requirements are considered runnable.

<details><summary>Risk Details</summary>

- New global/resolver options, destination `platform` parameters, and the public routing helper become administration interfaces that deployed sites and routing rules will depend on.
- Existing tool requirement sets must resolve together consistently across native and foreign paths; accepting individual environments that cannot be used simultaneously breaks downstream jobs.
- Shared filesystem creation, backfill, failure retry markers, deletion, and cross-process locks affect persistent environments used by concurrent jobs.
- The signing and activation protocol must remain compatible with real Conda packages and the configured operating system; a marker should represent a usable environment.
- Defaults mostly keep platform-specific behavior opt-in. Core platform metrics and the new test imports change behavior even when `conda_platforms` is unset.
- Disabling the options rolls back most runtime behavior and leaves additional environment directories on disk; this is relatively reversible, but configurations and routing contracts become harder to change after adoption.

</details>

<details><summary>Risk Review Advice</summary>

Human reviewers should first establish the environment contract: whether a tool requires one combined environment, how contextual/native resolvers remain supported, and which destinations are actually containerized. Tests should cross the routing-to-command-execution boundary for those cases. Separately review prefix sharing, cleanup while jobs run, actual Conda installation semantics, and macOS signing on the author's rig; fake binaries and a local activation probe do not establish those cross-host guarantees.

</details>
