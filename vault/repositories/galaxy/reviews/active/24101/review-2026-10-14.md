## Finding

**P2 — Keep the truncation warning in the embedded graph** (`client/src/entry/widgets/HistoryGraph.vue:19`, template at line 37).

`useHistoryGraph` requests at most 500 top-level history items and exposes `isTruncated` from the API's `truncated.item_count_capped`. The existing `HistoryGraphView` shows a warning when this occurs. The new widget drops that return value and renders the graph without any completeness indicator. On a large history, consumers see a partial provenance graph as if it covers the history; no full-view context in the widget explains the omitted items.

Retain the cap, but consume `isTruncated` and display a short warning before the canvas. Add a widget render regression with a capped response. A component-level probe supplied nonempty graph data and `isTruncated=true`: the real widget renders the canvas and no warning. The expected-warning assertion fails on HEAD and passes with an in-memory transform that only consumes the flag and adds an alert. The probe stubs graph rendering/data, so it does not claim an actual 501-item browser run.

## Architecture and coverage

The canvas extraction reuses the real graph renderer, color mapping, layout and focus behavior. API discovery has typed metadata and its route/parameter names match the widget router. Production entry bootstrap reuses Galaxy initialization, Pinia and app plugins; it avoids the analysis navigation shell. No weakened tests or independent graph implementation found.

The discovery API and router tests cover metadata and route mapping, but neither executes the complete browser bootstrap. A browser smoke test covering initial rendering, the configured URL prefix, an inaccessible history and live updates would strengthen this new entry point. This is coverage advice, not a second blocker.

Cross-origin embedding needs an explicit deployment contract: Galaxy still defaults to `X-Frame-Options: SAMEORIGIN` (`config_schema.yml`), and this PR does not change that. Document the supported deployment/proxy and authentication setup for external applications; do not assume the new route changes existing frame policy. This is an operational integration constraint, not a new security finding.

## Risks

The public widget catalog and URL/parameter contract are one-way API choices for external applications, although the canvas refactor itself is easy to roll back.

<details><summary>Risk Details</summary>

- External consumers can depend on `history_graph`, the route template, encoded IDs and seed query parameters.
- An incomplete graph must be clearly marked so consumers do not misread provenance.
- Each embedded widget starts its own user/history loading and watcher lifecycle; multiple embeds can multiply requests.
- Frame policy, authenticated browser sessions and SSE/polling behavior determine whether an external deployment can use the widget as advertised.

</details>

<details><summary>Risk Review Advice</summary>

Confirm the stable catalog contract and supported embedding setup before treating this draft as ready. Validate the complete entry point in a browser, including prefixed deployment and a capped graph. Preserve the existing API access checks and frame policy while defining the intended integration.

</details>
