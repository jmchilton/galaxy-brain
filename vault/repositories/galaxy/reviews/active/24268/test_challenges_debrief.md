## Challenge of each new/changed unit test

### Keep
- **FormDrilldown.test.js** (6 new cases): they test behavior through the DOM: checked state, select-all emits, indeterminate, one shared radio name, separate names per instance. The two-instance case guards the `useUid` choice (the workflow run form renders the same parameter id more than once), which is a real regression risk. Good.
- **FilterMenu.test.ts**: after clicking, the `.g-checked` checks cover the new local `selected` ref in `FilterMenuBoolean` (FilterMenu stages changes in a non-reactive computed object). Without the ref the shown choice would not update, so these assertions protect the PR's only logic change outside the drilldown. The `role`, `aria-label` and shared-name checks are fine.
- **GRadioGroup / GCheckboxGroup `legendClass`**: small prop contract test. It checks the class lands on the legend and not on the group, and that the attribute doesn't fall through. Fine.
- **LabelSelector, Toolshed/Index, ThemeSelector** (new files): v-model wiring after the swap, plus the per-caller accessible name. Under `@vue/compat`, the BFormRadio to GRadio v-model wiring is a plausible break, so these earn their place.
- **InstallationSettings** new case: it goes end to end from the msw-mocked configs to a radio choice to the `ok` payload. Good shape (see P3 2 for trims).
- **tokensContract.test.ts**: regex widened for half-step shades; needed.

### Rewrite or trim
- **MarkdownEditor.test.ts**: the first case asserts `d-inline-block`, `g-outline`, `g-blue` and `g-small`. These are styling details the screenshots already cover, and they break on any visual retune. Keep the button labels, the checked "Text" and the stub swap.
- **FilterMenu.test.ts** loop: `classes()).toContain("g-radio-button")` asserts that button mode is drawn with a given class. Drop it; the `.g-radio-button` locator use further down is enough.
- **CopyModal.test.ts**: the first case asserts the child's `props(...)` (label, stacked, modelValue, option values). That tests the template binding, not behavior. The second case sets the choice with `vm.$emit` on GRadioGroup rather than a user action. Merge the two: find the radio whose label reads "all datasets", `setValue(true)` it, confirm, and assert `copyHistory(..., true)`. Optionally assert the legend text through the DOM.
- **HistoryImport.test.js**: it reads `wrapper.vm.howLabel` and `wrapper.vm.importType`. Assert the literal legend text and that the upload field appears; the URL-input-gone check is already there.
- **ThemeSelector.test.ts**: the module-level `currentTheme`, `settingTheme` and `setCurrentTheme` are shared across cases and never reset. `settingTheme.value = false` runs after the assertion, so one failure leaks into the later tests. Move the resets into `beforeEach` (with `vi.clearAllMocks()`).
- **InstallationSettings** new case: it checks the label twice (the `aria-labelledby` lookup and `legend.text()`), and `parentElement.closest("fieldset")` pins the DOM nesting. Keep one label check; drop the nesting probe unless a nested-fieldset a11y bug is the intended guard.

### Mocks
- ThemeSelector's `vi.mock` of `useConfig` and `useCurrentTheme` is the normal pattern; no reusable fake is available.
- MarkdownEditor and Toolshed/Index stub child editors and lists, which is appropriate.
- No SimpleNamespace-style constructs to replace.
