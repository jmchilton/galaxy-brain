This is a one-way door for bytes, not for APIs: it starts irreversibly deleting metadata files (e.g. BAM indexes) on every purge path, and its safety rests on each `metadata_file` row owning its own file, which `store_by: uuid` deployments with duplicate uuids may not satisfy.

<details><summary>Risk Details</summary>

- Deletion cannot be undone. Once merged and run, removed metadata files are gone. The code can be reverted, but anything deleted wrongly can only be regenerated by re-detecting metadata, and only if the primary data still exists.
- Possible shared files under `store_by: uuid`. The file name comes from the row's uuid, and `metadata_file.uuid` is not unique in existing databases: `lib/galaxy/model/metadata.py` says so, and `replace_metadata_file` in `lib/galaxy/model/store/__init__.py` deliberately inserts a second row with the same uuid for a different dataset instance. Two such rows name the same `metadata_<uuid>.dat`, so purging one association would remove the file the other still uses. The PR's caveat covers one row shared by an HDA and an LDDA, not two rows sharing a uuid. This comes from reading the code and was not reproduced.
- Library purge no longer waits for the dataset. `delete_library_datasets` now removes LDDA metadata files while the same `Dataset` is still live through an HDA. The PR calls out this departure from the legacy script. It depends on the same one-file-per-row assumption.
- `--force-retry delete_library_datasets` becomes a bulk historical delete. It targets every deleted library dataset past the retention window, including those purged long ago, so the first run on a large instance could remove many files at once.
- `purged = true` does not guarantee the file is gone. In `pgcleanup`, flags are set by SQL, but physical removal can be skipped (user-defined object stores) or fail with only a log line. The new `purged IS NOT TRUE` filter means later `--force-retry` runs won't try those files again, so they stay orphaned.
- `full_delete()` has more ways to fail. It has eight call sites, including job finish and `copy_from`. Any object store error other than `ObjectNotFound` on a metadata file now raises before the primary dataset is deleted, and some callers swallow exceptions, so a dataset purge could fail or quietly do nothing.
- Purging datasets with many associations costs more. `full_delete()` now loads all history and library associations, then makes one object store delete per metadata file inside the purge request or job finish path. This matters most on remote stores.
- Existing API-purged HDA leftovers stay. As the PR's table shows, `purge_datasets` has no metadata handling and purged HDAs are skipped, so the library side gets a reclaim path and the history side does not. Operators should not expect space back from earlier HDA purges.

</details>

<details><summary>Risk Review Advice</summary>

The question to settle first is whether two `metadata_file` rows can resolve to the same object store path in production data. Check how duplicate-uuid rows arise on import and whether `usegalaxy.*` databases have any across different associations. If they do, deletion should skip a file while another unpurged row holds the same uuid, in both `_delete_metadata_files()` and the `pgcleanup` CTE.

Also decide whether release notes should warn admins before the first `--force-retry delete_library_datasets` and suggest a `--dry-run` or a backup. Then consider whether a metadata file failure should be able to block purging the primary dataset, since `full_delete()` runs on job and copy paths that were not written with this new failure in mind.

</details>
