## Findings

### P1 — Preserve Python 3.8 compatibility in runtime callback types

Location: `lib/galaxy/tool_util/parameters/convert.py:613–614`, also the new nested annotations at lines 665 onward.

The new `Callable[[..., list[str]], ...]` aliases evaluate `list[str]` when the module imports. Python 3.8 cannot subscript the builtin `list`, so importing `galaxy.tool_util.parameters.convert` now raises `TypeError: 'type' object is not subscriptable`. Both `galaxy-tool-util` and `galaxy-tool-util-models` still declare `python_requires = >=3.8`; this breaks supported Pulsar/package consumers before tool execution.

The [Pulsar Python 3.8 CI job](https://github.com/galaxyproject/galaxy/actions/runs/37958242344/job/113914155911) points directly to the new alias and ends with **130 collection errors**. Independent execution of both exact AST-extracted alias definitions on local Python 3.8.20 reproduces the failure; replacing `list[str]` with the already imported `typing.List[str]` passes. The probe substitutes `Any` for unrelated model types, so it is an isolated execution probe, not a second full package-import test. CI supplies the real import trace.

Use `List[str]` for the newly introduced uses in this module. A future-annotations import alone does not defer a type-alias assignment's right-hand side; nested callback annotations should also remain compatible when `runtimeify` executes on Python 3.8. Reproducer: [python38-probe.py](python38-probe.py).

### P2 — Give the new regression fixture distinct input and output names

Location: `test/functional/tools/implicit_conversion_shared_input_y.yml:17–24`, and the corresponding test output keys at lines 35 onward.

The new outputs reuse both input names (`as_fasta` and `as_tabular`). Existing `DefaultToolAction.execute` creates those output HDAs, but its history-addition loop at `lib/galaxy/tools/actions/__init__.py:775` intentionally skips an output whose name exists in `incoming` (the legacy async-data-source path). Both new outputs therefore remain without history/HID.

The required [framework CI job](https://github.com/galaxyproject/galaxy/actions/runs/37958242485/job/113914154342) fails specifically on this new fixture. Both stored artifact reports contain **615 passed, 1 failed**, with `HistoryDatasetAssociation ... without history detected, this is not valid`. A normal local run passes because it does not enable `GALAXY_TEST_RAISE_EXCEPTION_ON_HISTORYLESS_HDA`. Enabling CI's strict flag reproduces the failure locally, while all three selected XML conversion siblings pass.

A constructor trace identifies the orphan as a `txt` output created by `DefaultToolAction.handle_output`, not an implicit-converter dataset. The output-name guard is unchanged on the base branch: this new fixture exposes an existing name-collision behavior; the conversion lookup does not introduce that behavior. Rename the outputs and expected-output keys, for example to `as_fasta_out` and `as_tabular_out`, retaining the input names, paths, and stdout assertion. [renamed-fixture-probe.py](renamed-fixture-probe.py) applies only those names in memory; the strict end-to-end run then passes (**1 passed**, 615 deselected, 32.53s), without changing Galaxy source.

## Implementation and coverage

The latest commit incorporates Marius's earlier shared-input feedback. The runtime now indexes converted job inputs by their original HDA and passes each parameter's accepted extensions through dataset, multiple-dataset, collection, and DCE conversion callbacks. Looking up the original first and checking datatype compatibility matches the direct-versus-converted choice made by `DefaultToolAction`/the datatype registry. The change reuses `datatype.matches_any`; no separate matching algorithm is introduced.

The new end-to-end tool fixture is the right building block for the important case: the same uploaded fasta reaches one direct fasta input and one implicitly converted tabular input, and both the actual file contents and reported formats are asserted. Its names need the correction above. Broader coverage can cleanly reuse the framework tool harness and existing XML collection fixtures; no browser, remote data source, or distributed runner is needed. Additional collection/mapping integration coverage would be useful but is not another merge requirement here.

## Risks

The implementation is reversible and introduces no migration or new API field, but correct dataset selection is essential to tool execution; current package compatibility and regression-test failures must be resolved before merging.

<details><summary>Risk Details</summary>

- A wrong input lookup can silently give a YAML parameter the original dataset instead of its requested conversion; shared-input, collection, and multiple-input paths deserve attention.
- Parameter models now carry declared formats instead of the generic default; this restores the intended existing tool contract but touches the shared tool-util package.
- Python 3.8 import compatibility affects standalone package and Pulsar users, beyond the YAML feature itself.
- Rollback is straightforward, but restores the previously broken implicitly converted YAML-input behavior.
