## Finding

### P2 — Keep XML-incompatible keys on individual deletes

Location: `lib/galaxy/objectstore/s3_boto3.py:379–385`.

The new batch API embeds every listed key in an XML document. An extra-file key containing an XML 1.0-incompatible character, for example `000/dataset_1_files/control\x01name`, is valid in S3 and in a Unix filename. boto3 automatically requests URL-encoded listings and decodes them, so `_keys` returns that exact character. `delete_objects` then serializes it literally into its XML payload. An XML-validating service rejects the whole request with `MalformedXML`; that error takes the non-fallback branch and terminates cleanup, including normal keys in that batch and any later batches. The old individual-delete loop URL-encodes the key into its DELETE request and succeeds for the same key.

The [AWS ListObjectsV2 API documentation](https://docs.aws.amazon.com/AmazonS3/latest/API/API_ListObjectsV2.html#API_ListObjectsV2_RequestParameters) explicitly describes supported object keys that cannot be represented in XML and the URL-encoding option. The [DeleteObjects API](https://docs.aws.amazon.com/AmazonS3/latest/API/API_DeleteObjects.html) requires XML. The local test shows the actual SDK serialization and response handling, with a standard XML parser enforcing that restriction; it is not a live AWS test.

Prefer separating XML-unsafe keys and deleting those individually while keeping ordinary keys batched. A payload-specific `MalformedXML` fallback is another option, but it should not permanently disable batching for an otherwise capable endpoint. Add a real-client HTTP regression with one unsafe key and one normal key, and assert both are removed. Carriage returns and line feeds alone do not reproduce this bug: botocore's before-call handler correctly escapes them.

Prevalence is unmeasured and these filenames are unusual. No impact is demonstrated for ordinary filenames. The regression matters because cleanup previously supported these keys, and one such key blocks all other keys in the request. Retrying the same cleanup repeats the malformed request. Recovery requires individual-key deletion, isolating the problematic key, or restoring the previous implementation. Existing pgcleanup and Dataset.full_delete callers ignore the object-store boolean result; that pre-existing behavior can mark data purged while remote files remain, but is not a separate finding introduced here.

## Architecture and coverage

The normal path is clear and appropriately uses `chunk_iterable` rather than materializing the full prefix. Its 1,000-key limit, paginator continuation, short-page behavior, empty prefixes, partial errors, fatal errors, endpoint-scoped capability cache and individual-delete failure handling are well covered. Reusing `_delete_existing_remote` preserves error logging for fallback and lets later keys continue. One shared endpoint capability cache is reasonable; concurrent discovery can cause repeated rejected requests but does not change deletion results. The cache lasts for the process lifetime, so a backend capability upgrade requires process restart before batching resumes. This is a performance limitation, not a correctness blocker.

The sibling boto/cloudbridge/Azure backends retain their own single-delete implementations, which is consistent with this PR's boto3-only scope. Primary dataset deletion and path construction are unchanged. No tests were weakened. The existing HTTP test already exercises actual client configuration, XML error parsing, and fallback, beyond pure stubbing. A production speedup has not been measured; reducing request count is established by tests, but real wall-clock performance is not.

## Integration-test building blocks

A clean backend integration test is feasible with `BaseSeaweedFSObjectStoreIntegrationTestCase` in `test/integration/objectstore/_base.py` (also aliased as `BaseSwiftObjectStoreIntegrationTestCase`). It owns the disposable SeaweedFS container, boto3 object-store config, cache directory and DatasetPopulator. Composite-output fixtures already run in `test_swift_objectstore.py`; `test_remote_objectstore_cache_operations.py` demonstrates purge through the API.

A useful new test would generate more than 1,000 nested extra files for one dataset, seed a neighboring dataset/prefix sentinel, purge, and independently list the backing bucket to assert all target files disappeared and the sentinel survived. Assert remote keys, not just the API's `purged` flag or cache absence. If claiming the pgcleanup route specifically, `test/integration/test_scripts_pgcleanup.py` and `BaseScriptsIntegrationTestCase` provide script execution, but require PostgreSQL and would need the S3 config composed into that harness. The API-purge test is the simpler backend integration, while pgcleanup end-to-end validation is heavier. The deterministic local HTTP regression is the cleanest coverage for XML-incompatible filenames and checksum errors, whose behavior varies among emulators. These integration additions were assessed, not implemented or run.

## Risks

The implementation is easy to roll back, but deleting remote dataset files is a one-way operation; correct key selection, complete cleanup and backend compatibility deserve focused review.

<details><summary>Risk Details</summary>

- Batch deletion changes request encoding and exposes the XML-incompatible-key regression above.
- A request can partially succeed; this PR correctly logs per-object failures, returns false, and continues later batches. Existing purge callers still do not consume that false result.
- Endpoint capability detection is cached across stores within a process. One backend rejection affects subsequent buckets on that endpoint, preserving correctness via slower individual deletes.
- There are no migrations, persisted configuration changes or API contract changes. Rolling back restores the single-request-per-key implementation.
- No live AWS/S3-compatible deployment, production latency benchmark or heterogeneous backend compatibility matrix was tested in this review.

</details>

<details><summary>Risk Review Advice</summary>

Storage maintainers should verify the target EU endpoint's error codes and confirm that its batch delete semantics match the real-client tests. Retain independent bucket-list assertions for destructive cleanup and isolate payload-specific errors from endpoint-wide capability decisions. A focused S3-backed purge test would strengthen confidence without requiring every stubbed error case to become a full Galaxy integration test.
