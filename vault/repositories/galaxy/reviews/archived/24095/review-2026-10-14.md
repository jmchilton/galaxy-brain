Reviewed `d86df284fbe61dfe3a0f3c837c37359865a43369` against `dev`, 2026-10-14. Open, ready; final head unchanged, no comments or reviews. Recommendation: **request changes for one P2**, plus one non-blocking configuration-validation note. Review remains unposted.

## Finding

**P2 — Resolve path-relative extension URLs against the Galaxy root** (`client/src/components/admin/AdminPanel.vue:48`; also the shared `CenterFrame` path used by `AdminExtensionItem.vue:33`).

The new schema promises that relative URLs resolve against Galaxy's root. A valid plugin entry `url: static/welcome.html` is accepted, but both targets pass it through `withPrefix`, which only prefixes strings starting with `/`. The resulting anchor/iframe URL remains `static/welcome.html`. Under `/galaxy/admin/users`, the browser resolves that to `/galaxy/admin/static/welcome.html`; under the framed route `/galaxy/admin/extensions/example/page`, it becomes `/galaxy/admin/extensions/example/static/welcome.html`. The intended `/galaxy/static/welcome.html` is never requested, and the catch-all client route can display the Galaxy app instead of the configured page.

Normalize path-relative entries at the new extension boundary for both targets, retaining actual external URLs, or reject/document them explicitly instead of claiming root-relative resolution. Prefer a shared helper so the framed and new-tab cases cannot diverge.

A render probe mounts the real Admin panel and real CenterFrame with app root `/galaxy/`. Both produce an unprefixed URL for `static/welcome.html`. Leading-slash and absolute HTTPS controls pass. The three-case suite has one failing case containing both failed assertions on HEAD, and all three cases pass when an in-memory helper transform prefixes the path-relative input. Standard URL resolution independently confirms both wrong destination paths. The control establishes the failure mechanism, not a proposed unrestricted change to the shared helper.

## Non-blocking note

**P3 — Validate item IDs are unique within an extension.** `AdminExtensionLinkItem.id` documents this requirement, but `AdminExtension` accepts duplicate item IDs. The manager and client lookup then select the first matching item, so two framed entries with the same ID navigate to the same first URL. A schema/manager probe accepts `/first` and `/second` with id `same` and returns `/first`. Consider rejecting such configs with a useful validation error. This is an administrator configuration mistake, not a blocker on its own.

## Architecture and coverage

It uses existing DI registration, Pydantic models, `config_directories_from_setting`, the admin route tree, Pinia, and CenterFrame. No existing abstraction for this complete link registry was identified; the custom loader is small and typed. Additional manager lookup methods have no current backend caller, but no broad refactor is needed to address the finding.

The API is admin-only and has real integration coverage for admin listing, non-admin refusal, and empty configuration. Supplied client tests keep existing Admin panel assertions and add both target types. A browser navigation test with a prefixed Galaxy and both URL spellings would cover the gap found here. The loader follows sibling plugin directory resolution; default sample config is not activated.

## Risks

The API and plugin YAML establish a lasting administrator configuration contract; the presentation changes are otherwise easy to roll back.

<details><summary>Risk Details</summary>

- Administrators will depend on the identifiers, target types, directory structure and relative-URL semantics.
- Both target types must resolve the same configured URL consistently, including a Galaxy URL prefix.
- Configs load at startup; editing or installing extensions requires a restart, and malformed configs are skipped.
- Framing external applications depends on those applications' own embedding policies; a successful catalog request alone does not prove the page can be displayed.

</details>

<details><summary>Risk Review Advice</summary>

Settle URL normalization and duplicate-ID behavior before encouraging plugin authors to adopt the format. Check the sample extension in a prefixed Galaxy for framed and new-tab navigation. Keep the declarative links scope and existing admin-only API boundary rather than expanding this PR into a general plugin settings system.
