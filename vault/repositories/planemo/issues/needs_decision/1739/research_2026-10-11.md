# Research — Reusing CLI validation for configuration

Date: 2026-10-11. Requested by John after the CLI/config Python-choice discrepancy in Marius’s #1704 review. Result: filed [#1739](https://github.com/galaxyproject/planemo/issues/1739) for the remaining design gap; #1667/#1714 already cover normal type conversion.

## Findings

Planemo global configuration is lazy-loaded YAML, not a validated configuration model. `read_global_config` returns `yaml.safe_load` directly; `PlanemoCliContext.global_config` turns falsy contents into `{}`. `_find_default` pulls recognized keys for the current command; it does not check the root’s shape, unknown keys, or unrelated settings. Separately, `sheds`, `github`, and `lint_skip` are read outside generic default blending.

Global defaults enter through a parameter callback after Click has converted its original input. Before #1714 this permits unconverted values from YAML. #1714’s `convert_option_value` calls Click’s `type_cast_value`; it therefore restores choices, paths, booleans, multiple values, and `nargs` for defaults and matching profile options. Global defaults then run the existing outer callback, while profile values are blended in `command_function` after all option callbacks. The profile helper does type conversion but does not run those callbacks. Profile settings without a matching command option remain untouched by design.

The option decorators already attach `planemo_config` metadata, and `cli_metadata.py` exports that metadata along with choice/range/path constraints. This is useful discovery infrastructure for a configuration checker, not a validated configuration schema. Actual Click types remain authoritative, especially for custom types that serialized metadata cannot express fully.

Click provides [Context.default_map](https://click.palletsprojects.com/en/stable/commands/#overriding-defaults) for config-derived defaults. In the installed Click 8.4.1, a native default_map choice probe also rejects an invalid value. [Callbacks](https://click.palletsprojects.com/en/stable/advanced/#callbacks-for-validation) can perform additional validation after type conversion. `process_value` includes callback invocation; calling it again after Planemo blending risks re-entering the sourcing wrapper, double conversion, and callback side effects. A design should either isolate pure validators or source effective values before normal Click processing. Neither default_map nor type conversion supplies Planemo-specific YAML shape/key validation automatically.

## Evidence and limits

Checked upstream master `48725d692ee3371ace6a042b70ec3dc84a3b0ba6`, #1704 `c38e6c179149baf424bd005f6fd400e96276c86d`, and #1714 `6a9c35a56c1e50c63163187a4afcc151cd67f4ac`. Duplicate searches covered config validation, config lint, configuration schema, unknown config, and profile callbacks. #1667 is related; closed #157 covered config tests, and #933 concerns Galaxy tool XML values rather than Planemo configuration.

The probe uses real option blending, temporary YAML files, and on-disk profiles with the existing `docker_galaxy` profile branch. It runs no command that launches Galaxy, a container, or a database, and makes no network calls. Two source passes each exercised twelve cases. For #1714 the Python option is a small `planemo_option` using #1704’s explicit choice list: this isolates compatibility of the helper and constraints, and is not a full merged-branch integration run. ## Issue scope

The filed issue proposes an explicit offline lint entry point with shared Click definitions and minimal contracts for nested/internal settings. Open decisions include warning versus strict errors for unknown keys, path policy, effective-value validation versus checking all stored defaults, shadowed invalid values, conflicting option definitions across commands, and safe callback reuse. Diagnostics must identify file/profile/key without exposing credential values. Existing CLI/environment > profile > global config > declared default precedence and aliases should remain part of acceptance coverage.
