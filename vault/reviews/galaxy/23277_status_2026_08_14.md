## New this round

### 1. The generic `metadata` deserializer is now live on the modern dataset API

`70718a0ee` adds `"metadata": self.deserialize_metadata` to
`DatasetAssociationDeserializer.deserializers` (`lib/galaxy/managers/datasets.py:880-886`).
Before this commit that method was dead code carrying a `# TODO: untested` marker. After it,
`PUT /api/datasets/{id}` with a nested `{"metadata": {...}}` body sets **any non-readonly
metadatum on any datatype**, not just Crypt4GH — `deserialize_metadatum` filters only on
`metadata_spec` membership and the `readonly` flag.

Two consequences:

- It is a **core API behaviour change with a global blast radius**, arriving inside a
  Crypt4GH feature branch, with `validate_crypt4gh_compute_metadata()` called unconditionally
  from the generic per-datum path. It deserves separate sign-off from whoever owns that
  manager, independent of the Crypt4GH decision.
- It **closes off the copy-stripping mitigation on its own terms.** Even if
  `crypt4gh_compute_*` were stripped on every copy/import path, Alice can read Bob's compute
  header off the shared dataset (`crypt4gh_compute_header` is `readonly=False, visible=True`)
  and simply `PUT` it back onto her own copy. Stripping is no longer even a complete stopgap
  — the write channel is a supported generic API.

This is not an accident of the port: the pre-port branch has the same change, committed as
"Galaxy change: Activated existing 'deserialize_metadata'". It is the mechanism the recrypt UI
uses.

### 2. First tests exist — happy path plus one negative, no authorization test

`lib/galaxy_test/selenium/integration/crypt4gh/` covers: single encrypted input, multiple
encrypted inputs, mixed encrypted/plain, and `test_run_cat_without_compute_metadata_fails`
(readiness guard rejects a dataset with no compute metadata), plus a workflow suite. Outputs
are downloaded and decrypted for real. That is meaningful coverage and the right scaffolding.

Two gaps worth raising *now*, while the scaffolding is a day old:

- **No cross-user test.** The suite has exactly the fixtures to express it — a second
  registered user, `upload_crypt4gh_dataset` for Bob, share/copy, run `cat1` as Alice. That
  test is the executable form of the design decision: it either passes (sharing grants
  compute) or fails before Service B is contacted (owner-only). Writing it forces the policy
  question to be answered.
- **The mock recryptor bakes in the unauthenticated contract.** `mock_recryptor.py`'s
  `_handle_recrypt_to_job_key` takes header + job public key and recrypts, with no principal,
  no token, no rejection path. It is now the reference implementation of the Service B
  interface inside the Galaxy test suite. Whatever authorization lands should be asserted
  *here* — a mock that rejects an unauthorized request is where the invariant gets teeth.

### 3. sveinugu's regression and our P1-9 have the same root cause

He says he "moved the encryption of discovered outputs from a separate implementation that
started to reimplement the existing output discovery code in Galaxy, into the existing code
itself to remove duplication," and asks whether those changes were lost in the port.

That is our P1-9 stated from the other direction. The PR as it stands re-implements pattern

## How sveinugu's proposal relates to ours

Short answer: **mostly the same puzzle piece at a different resolution, plus one piece of ours
that is genuinely orthogonal and that his proposal quietly depends on.** Three layers, and they
sort cleanly.

### Layer 1 — where the delegation lives in Galaxy (orthogonal; needed under both)

Our grant model replaces copyable HDA metadata with a server-managed record keyed on
`(user, dataset, destination)`. sveinugu's comment says nothing about this layer.

But his mechanism *presupposes* it. "A secure token, stored Galaxy-side in the vault, presented
to the compute-side recryptor" only discriminates if the compute-side Galaxy looks the token up
by **the job's user** (`job.user_id`). If it looks it up from the dataset's own metadata — which
is where every other Crypt4GH value currently comes from — then Alice's job presents Bob's
token automatically and the extra factor closes nothing. So Layer 1 is not an alternative to his
idea; it is the thing that makes his idea work at all.

**This is the single most useful question to ask him**, and it is a design question, not a
criticism: *whose* token does the compute side present for a job — the job user's, or the one
recorded on the dataset?

### Layer 2 — what Service B checks (these are alternatives)

Here the two proposals genuinely compete. His: Crypt4GH sender-key validation plus a long-lived
per-user secret. Ours: a short-lived signed authorization binding user + dataset + grant + job +
job public key.

| | sender-key + per-user token | grant + job-scoped signed authz |
|---|---|---|
| Binds to a user | yes, *if* keyed on `job.user_id` | yes |
| Binds to a dataset | no — any dataset of Bob's | yes |
| Binds to an active job | no | yes |
| Binds to the presented job public key | no | yes |
| Revocable | only by rotating the user's key/token globally | per grant |
| Replay-resistant | no | yes (`exp`, `jti`) |
| Where the decision is made | Service B, by comparing key material | Galaxy decides, Service B verifies |
| Cost | payload field + vault storage | new model, migration, endpoint, protocol change |

### The prerequisite his idea has, which the current code does not satisfy

Sender validation is real — `crypt4gh.header.decrypt_X25519_Chacha20_Poly1305` takes
`sender_pubkey` and rejects on `sender_pubkey != peer_pubkey`, where `peer_pubkey` is read out
of the packet. But the sender key stamped on a packet is
`derive_pk(seckey)` for whatever secret key the *re-encrypting* party passed in `recipient_keys`
(`crypt4gh/header.py`, `encrypt_X25519_Chacha20_Poly1305`).

The PR's own mock Service B generates a **fresh ephemeral sender key per recipient**:

```python
# crypt4gh_test_utils.py — reencrypt_header()
# Generate an ephemeral sender key for each recipient
for recipient_pub in recipient_public_keys:
    ephemeral_priv = X25519PrivateKey.generate()
    ...
```

So under the contract the Galaxy test suite now encodes, a compute header carries **no stable
user-identifying sender key** — validating against Bob's public key would compare it to a random
ephemeral key and fail for Bob as readily as for Alice. For his proposal to work, Service A must
seal the compute header with the *user's own* private key as sender, which is a change in the
recryptor service and carries a linkability tradeoff (a stable sender key makes all of Bob's
headers correlatable — which is presumably why ephemeral is the default).

The real service shells out to a Rust `crypt4gh-recryptor recrypt` binary
(`crypt4gh_recryptor_service/crypt.py`), so what *it* stamps is worth confirming with the
recryptor authors rather than assuming. Either way this is a question for them, not a defect
claim against this PR.

### And a scope distinction worth drawing for him

The two halves of his suggestion defend against two different attackers, and it is worth being
explicit because it affects how much the "public key becomes a secret" downside actually costs:

- **Sender-key validation** proves *this header was made by Bob's key*. It does not prove *this
  request is on Bob's behalf* — Alice's job presents Bob's header, so the check passes. Against
  the copy path, this half does nothing on its own.
- **The presented secret** (token, or the public key used as one) is what discriminates, and
  only because Alice cannot obtain Bob's copy of it. Its secrecy matters against a different
  attacker — wm75's scenario 2, someone with a shell on the compute node talking to Service B
  directly — not against Alice-inside-Galaxy, who never gets to choose the field.

That is the case for choosing **the token, not the public key**: the public key has legitimate
publication paths (it is how anyone encrypts to Bob), so making it a credential means a value
designed to be shared becomes one that must not be.

### The sequencing gift

If they pick the token now, his design **composes forward into ours without a protocol break**:
the payload shape stays the same and the token's scope narrows later from "per user" to
"per user + dataset + destination + job," with lifetime shortening from long-lived to job-scoped.
That is worth saying explicitly, because it means his proposal is a legitimate phase 1 rather
than a competing design to be argued down — and it makes Layer 1 (server-managed, principal-keyed
delegation state) the thing actually worth doing first, since both phases need it.

### Service B already has the user binding — it just isn't checked on the input path

This is the discovery that makes his proposal cheap, and it is good news.

`/get_compute_key_info` (`compute.py`) receives `user_public_key` from Service A, writes it as a
`HashedStrFile` under `user_keys_dir`, and allocates or reuses a compute keypair **keyed on that
user hash**:

```python
key_id_dir = ComputeKeypairFiles.lookup_last_exp_key_id_dir_or_create_new(
    settings, user_public_key_file.path.name)
```

The binding is persisted on the keypair as `user_hash`, and the **output direction already relies
on it**:

```python
# /recrypt_header_to_user_key
user_public_key_path = settings.user_keys_dir.joinpath(compute_keypair.user_hash)
```

That is why wm75 is right that outputs come back to Bob — Service B does not take the user key
from the caller on that path; it looks it up from the keypair.

`/recrypt_header_to_job_key` is the one route that never consults `user_hash`. It resolves the
keypair by id, checks expiry, and recrypts to the caller-supplied job key.

So the principal sveinugu wants to add **already exists server-side**. Adding
`user_public_key` to the `/recrypt_header_to_job_key` payload and comparing
`HashedStrFile(settings.user_keys_dir, params.user_public_key).path.name` against
`compute_keypair.user_hash` is a few lines in his service, with no new storage and no new model.
The gap is not "Service B has no concept of a user" — it is "the input path forgot to ask."

### What that implies for the Galaxy data model

Compute keypairs are allocated **per user** (one per user per expiry window), not per dataset. So
`crypt4gh_compute_keypair_id` is a per-user value that Galaxy currently stores as per-dataset
metadata and copies around with the dataset. The compute *header* is genuinely per-dataset; the
keypair id is not.

That sharpens Layer 1 rather than changing it: the natural Galaxy-side shape is a **per-user (and
per-destination) enrollment record** holding the keypair id and expiry, with **per-dataset
recrypted headers hanging off it** — instead of one flat metadata blob per HDA carrying both. It
also explains why the readiness guard cannot tell whose delegation it is: the field that identifies
the principal is stored in the one place that copies.

### One thing noticed in the service, offered as a heads-up

Service A is browser-facing by design and the app sets `allow_origins=['*']` with no
authentication dependency, so any page the user visits can POST to their local
`https://localhost:61357/recrypt_header` with an arbitrary header. The response is sealed to the
**compute node's** public key rather than a caller-chosen one, so this is not direct plaintext
recovery — but it does mean the user's private key acts as an open oracle to any website, and it
chains with an unauthenticated Service B if one is reachable. An origin allowlist is a cheap fix.
Low confidence on real-world impact, and it belongs in his repo rather than this PR; worth
mentioning as a courtesy, not as a finding against 23277.

## Assessment: is our input useful now?

Yes, and the window is unusually good.

- **The design question is open and unowned.** Everyone has agreed something is needed; nobody
  has proposed a concrete Galaxy-side mechanism. Our unposted
  [[23277_principal_bound_compute_grants_comment]] is exactly that proposal, and it answers the
  specific weakness in the only proposal on the table — sveinugu's "put the user's public key
  and a brokered token in the payload," which he himself flags as turning a public key into a
  secret, and which still binds nothing to a *job*.
- **Galaxy already has the primitive.** Pulsar job tokens
  (`lib/galaxy/jobs/runners/pulsar.py:680-699`, `lib/galaxy/webapps/galaxy/api/job_tokens.py:27-69`)
  are the existing pattern for "a compute-side process proves it is acting for one active job."
  That is the single most useful thing we can contribute: not "you need authorization" (they
  know) but "here is the Galaxy-shaped way to do it, and it is already in the codebase."
- **The tests are one day old.** Influencing the shape of the cross-user test and the mock
  recryptor's rejection path costs almost nothing today and gets much more expensive once the
  suite is settled and green.
- **davelopez is actively refactoring right now** and explicitly said the future-work items
  land "once the design is solid enough to set in stone." That is an open invitation on the
  design, and it is the moment before the metadata contract hardens.

Against posting: the thread is three days quiet, and a second long comment risks reading as
piling on. Mitigation is length and tone — the proposal comment is long; leading with the two
short concrete asks (cross-user test, metadata deserializer sign-off) and putting the grant
design behind a fold is better than opening with the architecture.

### Suggested shape of a follow-up

1. **Acknowledge the resolution.** sveinugu answered the question: authorization was assumed,
   not implemented. Nothing left to argue about the mechanism; the remaining question is
   sequencing.
2. **Answer wm75's fair objection directly.** Yes, declared outputs return to Bob's key, so
   this is not "Alice gets the file" in the normal path. The claim is narrower: Alice's job is
   handed plaintext it was never authorized to see, and the containment then rests on every
   egress path being closed — including the two the PR already admits are open. Confidentiality
   boundaries should not be enforced by the completeness of an output finalizer.
3. **Two small concrete asks**, both cheap right now: the cross-user Selenium test on the new
   scaffolding, and separate sign-off on the `deserialize_metadata` activation (with the note
   that it makes copy-stripping insufficient regardless).
4. **The grant + job-token proposal**, folded, pitched as one option and explicitly measured
   against sveinugu's token idea rather than replacing it.
5. **The discovery point as agreement, not criticism** — his own de-duplication instinct was
   right, and reinstating it fixes the admitted collection-element leak. Ask for the handoff
   branch so it can be diffed rather than rebuilt.
6. **Port the pre-port test assets** instead of writing the Future Work unit tests from
   scratch.

7. **Answer the Pulsar idea rather than ignoring it.** The instinct is right and is the same
   instinct as ours: put the check where every output path converges, instead of predicting
   discovery ahead of time. Pulsar's stage-out is one such convergence point, and validating
   there would catch `from_work_dir` and discovered outputs without re-implementing discovery.
   But it does not follow that Pulsar should be *required*: the convergence point exists
   Galaxy-side too (the discovery/persistence seam in `model/store/discover.py`), it works for
   non-Pulsar destinations, and Pulsar configured against a shared filesystem stages nothing,
   so the funnel it relies on is a property of one staging mode rather than of Pulsar. Framing
   it as "you already identified the right property; here is where to get it without the
   dependency" is more useful than either endorsing or dismissing it.
